# ADLIB: восстановленный C и точность рекомпиляции

## Что доказано

Участок `1341:1E1A..2E9B` занимает **4225 байт** и содержит **52 процедуры**. Все 52 имеют определения в `full/sound/ADLIB.C`; заглушек вместо содержательных алгоритмов нет. Две процедуры, `28FB` и `2BC4`, содержат короткие вставки ассемблера для вызова аппаратного интерфейса с номером канала в `AH`. Пустая `23D1` действительно состоит в оригинале из `RET`.

Существуют три раздельных результата:

| Результат | Проверенный статус |
|---|---|
| Читаемый C, типы и алгоритмы | Все 52 определения присутствуют; Microsoft C 8.00 компилирует их в один объект |
| Поведение отдельно взятой C-процедуры | **2404 из 2404 сравнений** прошли для всех 52 процедур; ограничения метода описаны ниже |
| Побайтовая рекомпиляция всего участка из этого C | **Не достигнута**: 4548 байт против 4225; текущий единый профиль не дал ни одной полностью совпавшей процедуры |
| Отдельная C-процедура `2665` | Microsoft C 5.1 дал **20 из 20 одинаковых байт**, включая действительные адресные привязки |
| Исполнимая спецификация `exact/ADLIB.ASM` | TASM 3.1 дал **4225 из 4225 одинаковых байт**, все 52 публичных адреса и адресные привязки совпали |

Полное совпадение ASM-спецификации и участие этого объекта в точной сборке игры **не доказывает рекомпиляцию звука из C**. ASM-файл является восстановленным символическим описанием инструкций. Он не объявляется историческим авторским исходником. В нём нет включения исходного EXE, бинарной подложки или массивов исполняемых машинных кодов; сборщик читает текст ASM и запускает TASM. Проверка читает эталонный EXE отдельным шагом.

Числа и подробные результаты находятся в `full/sound/adlib_c_coverage.json`, `full/sound/adlib_c_build/{compile,verify,semantic}.json`, `full/sound/adlib_c_build/msc51_small/verify_2665.json` и `full/sound/exact/module_adlib.json`. JSON для каждого entry содержит определение C, размеры, фактические начальные инструкции, различия пролога/сохранения регистров, адресные привязки и число семантических проб.

## Что именно проверяет эмуляция

`full/sound/semantic_vm.py` загружает DOS MZ образ как эталон среды, связывает одну скомпилированную C-процедуру по действительным OMF fixup и размещает её в свободном тестовом адресе `1341:F000`. Прямые внутримодульные вызовы, для которых компилятор уже записал относительное смещение без FIXUPP, отдельно связываются по известным PUBDEF. Это явная операция тестового связывания, а не исправление объекта для получения побайтового совпадения.

Затем оригинальная и C-процедура исполняются в Unicorn x86-16 с одинаковыми снимками памяти, аргументами и начальными регистрами. В обеих версиях все вызываемые процедуры остаются оригинальными. Это относится и к рекурсивным вызовам. Сравниваются:

- весь 64-килобайтный диапазон DS после возврата;
- `SP`, `BP`, `SI`, `DI`, то есть состояние стека и сохраняемых регистров;
- `AX` либо `AL` для процедур с используемым результатом;
- последовательность записей в аппаратные порты;
- аргументы явно обозначенных подменённых вызовов.

У метода две узкие подмены. При проверке `1FCC` ожидание аппаратного таймера `0496` немедленно возвращается, сохраняя регистры; сами OPL-записи сброса исполняются и сравниваются. При проверке `26C3` и её обёртки `22CD` вызов `2A5E` записывает три аргумента и возвращается: необычный указатель из оригинальной таблицы не разыменовывается. Причина последнего ограничения — описанное ниже поведение `DI`, а не желание скрыть различие C. Чтение аппаратных портов возвращает ноль, поэтому это проверка вычислений и последовательности записей, а не физического звучания AdLib.

Набор из 2404 проб включает все 256 состояний LFSR на пяти знаковых значениях, 567 сочетаний масштаба и значения плюс базовую пробу, по 150 дополнительных состояний обеих процедур огибающей, все 69 индексов таблицы полей, варианты канала и знаковых параметров партии, заполненный пул голосов, непустые списки с удалением головы/середины, ранний выход таймера и ветку повторного запуска через `AH`. Большинство остальных процедур имеют только одну базовую пробу. Это **не доказательство всех возможных входов и ветвей** и не запуск всего звукового модуля, полностью скомпилированного из C. В частности, C-процедура проверяется с оригинальными вызываемыми функциями; совместное поведение всех C-процедур и реальное аппаратное время этой проверкой не покрываются.

## Исправленные и сознательно сохранённые особенности

### Головы списков должны перечитываться

В исходных `20E7` и `2772` условие каждого оборота читает `player->parts` и `part->voices` из памяти. Функции удаления меняют эти поля через обратные ссылки `part->owner` и `voice->owner`.

Microsoft C 8.00 с выбранным оптимизированным профилем кэшировал такие поля в регистре, после чего цикл повторно передавал уже удалённый элемент. Это обнаружено исполнением и проверено по реальным инструкциям объекта. В восстановленный C внесены локальные `volatile`-приведения только при чтении двух голов. Структуры и ABI не изменены. Пробы с тремя элементами подтверждают совпадение памяти и завершение циклов. Это обоснованная защита поведения конкретной реконструкции; она не объявляется доказательством присутствия `volatile` в историческом исходнике.

### Поля счётчиков имеют размер один байт

`DS:58F2` — байтовый аккумулятор тактов; `DS:58F4` — байтовый индекс циклического выбора голоса. Следующие байты — отдельное хранилище/выравнивание, а не старшие части рабочих счётчиков. В `2B6C` видны `INC BYTE`, `CMP BYTE` и байтовое умножение. В тестах второй байт индекса намеренно установлен в `A5h`, чтобы ошибочное 16-битное объявление не прошло незамеченным. Общие определения в `SNDATA.C` согласованы с этим доступом.

### Ранний выход после первой истёкшей ноты

`1E1A` увеличивает байтовый аккумулятор на 3, при достижении 10 вычитает 10 и просматривает девять голосов. Истечение таймаута снимает текущий голос и немедленно возвращает управление, оставляя последующие голоса на следующий вызов. Это сохранено в C и проверено случаем с двумя одновременно истекающими голосами.

### Необычный аргумент в `25E7`

После поиска партии оригинал передаёт в функцию сброса bend младший байт указателя найденной партии как номер канала. Он не перечитывает исходный аргумент `channel`. C содержит явное `(ALByte)(unsigned)p` и комментарий. Исправление на предполагаемое намерение автора изменило бы поведение программы.

### Необычный указатель в `26C3`

В `1341:26E9` регистр `DI` заменяется адресом поля `shift` в описателе параметра. Перед вызовом `2A5E` код продолжает читать `[DI+6]`. Поэтому указатель списка голосов берётся из таблицы параметров, а не из `part->voices`. C специально воспроизводит эту адресацию. Проверка сравнивает изменённый байт инструмента и все три фактических аргумента последующего вызова по каждому из 69 индексов; дальнейшее разыменование такого указателя вынесено за границы пробы. Это наблюдаемое поведение, похожее на ошибку использования регистра; причина его появления не установлена.

### LFSR пересекается с последним слотом таблицы

Состояние LFSR находится в `DS:1100`, использует полином обратной связи `B8h` и одновременно попадает на младший байт физического последнего слова `snd_max_values`. Общий DATA сохраняет это пересечение адресов. Нельзя по этому бинарнику однозначно восстановить, как автор объявил длину массива и соседнюю переменную. В C и символических привязках важны фактические адреса и размер байтового доступа.

### Непереносимые свойства цели сохранены явно

Код рассчитан на 16-битные `int`, двухбайтные near-указатели, байтовую упаковку структур, арифметический сдвиг знакового `long` и расширения Microsoft C для near/inline ASM. Размеры `ALPlayer=18`, `ALPart=32`, `ALVoice=98`, `ALEnvelope=34`, `ALWork=8` проверяются при компиляции. Это компилируемый исходник для обозначенной DOS-модели, а не обещание корректной сборки современным 64-битным компилятором без адаптации.

## Почему профиль компилятора пока не установлен

Близость машинного кода к Microsoft C заметна, но одного похожего пролога недостаточно. Оригинал широко использует `ENTER n,0`/`LEAVE`, часто снимает один двухбайтовый аргумент двумя `INC SP`, не добавляет обычное межпроцедурное выравнивание; порядок сохранения `SI/DI` и распределение регистров неодинаковы. Текущий Microsoft C 8.00 часто выдаёт `PUSH BP; MOV BP,SP`, трёхбайтное `ADD SP,2`, другое назначение регистров и `NOP` в конце диапазона. Именно поэтому одинаковый алгоритм и даже одинаковая длина функции не дают одинаковые байты.

| Проверенный кандидат | Наблюдение | Что из этого следует |
|---|---|---|
| Microsoft C 8.00, `/AS /G2 /Gs /Oe /Ot /Zp1` | Все 52 определения компилируются; участок 4548 байт; 2404 семантических сравнения проходят | Рабочая диагностическая C-сборка, без доказанного исходного профиля |
| Microsoft C 5.1, `/AS /G2 /Gs /Zp /Oi /Os` | Текущий текст `2665` дал ровно 20 байт оригинала с действительными fixup | Одно доказанное совпадение C; общий модуль не доказан |
| Microsoft C 5.1, явный `register` в варианте `20E7` | `ENTER 0`, `SI`, форма цикла и `LEAVE` совпали; остаётся `ADD SP,2` вместо пары `INC SP`, 28 против 27 байт | Перспективная близкая форма, но всё ещё не точная рекомпиляция |
| Watcom 11.0c C16, `-2 -ms -s -os -zp1`, явный cdecl | На контрольных `1086/15F0` другие пролог, порядок загрузок, регистры и форма очистки памяти | Этот проверенный профиль не объясняет оригинал; более ранние версии этим не исключены |

Узкие варианты с `register`, `/Or`, старым объявлением вызываемой функции и `/G0`/`/G1` оформлены в `analysis/sound_register_profile.json`. Лучшие исходники и объекты сохранены в `full/sound/adlib_c_build/msc51_register` и `msc4_register`; они не изменяют canonical C и также не дают полного совпадения.

Исторический Watcom 9.5 C16 найден лишь в виде patchA без базового компилятора; это не пригодная для такой проверки toolchain. Часть ранних Microsoft/Zortech/Borland профилей проверена другими участками проекта; их отрицательные результаты не превращены здесь в категоричное утверждение об авторе или языке оригинала. Наблюдаемые странности `25E7/26C3` совместимы с ручной адаптацией машинно близкого ассемблера, но сами по себе её не доказывают.

Независимо найденная ранняя реализация ScummVM подтверждает близкое происхождение таблиц и алгоритмов iMUSE/AdLib: совпадают карта 16 параметров, таблица 32 длительностей, структуры огибающей и LFSR. C-реконструкция в этом проекте была написана до нахождения этого материала; текст ScummVM в неё не переносился. Это подтверждение алгоритмического родства, не точного авторского исходника или компилятора. Источник и точные совпадения записаны в `full/sound/adlib_provenance.json`: [первичная запись CVS от 19 декабря 2001](https://lists.scummvm.org/pipermail/scummvm-git-logs/2001-December/000086.html).

## Воспроизведение проверок

Из корня проекта можно заново получить диагностический C-объект оригинальным Microsoft C 8.00, передав собственные пути к компилятору и DOSBox:

```sh
python full/sound/compile.py full/sound full/sound/adlib_c_build ADLIB.C \
  --compiler /path/to/msvc10 --dosbox /path/to/dosbox \
  --flags='/AS /G2 /Gs /Oe /Ot /Zp1'
python full/sound/adlib_semantic_test.py full/sound/adlib_c_build/ADLIB.OBJ
```

Тест также принимает `--reference`, `--bindings`, `--crt`, `--output` и повторяемый `--function` с шестнадцатеричным offset. Пути по умолчанию вычисляются относительно самого проекта, а не рабочего каталога.

Для семантической проверки нужны Python-пакеты `capstone` и `unicorn`; эталонный `original/SNAKE.EXE` используется только в проверяющем коде. По одному примеру строгого сравнения C и всей ASM-спецификации:

```sh
python full/link/verify_object.py full/sound/adlib_c_build/ADLIB.OBJ \
  --function _snd_2665 --address 1341:2665 --length 20 \
  --bindings full/sound/bindings.json
python full/sound/exact/assemble_adlib.py \
  --compiler /path/to/BORLANDC --dosbox /path/to/dosbox
python full/link/verify_module.py full/sound/exact/adlib_build/ADLIB.OBJ \
  --segment _TEXT --address 1341:1E1A --length 4225 \
  --bindings full/sound/bindings.json
```

Первый пример сравнения с C ожидаемо сообщает отсутствие побайтового совпадения для Microsoft C 8.00. Для подтверждённых 20 байт следует вместо него указать `adlib_c_build/msc51_small/SMALL.OBJ`, полученный отдельным Microsoft C 5.1 с флагами из `msc51_small/compile.json`. Нельзя выбирать лучший профиль каждой функции и объявлять полученную сумму доказательством единого исторического проекта.
