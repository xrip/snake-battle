# SNAKE.GPF: контейнер, сжатие, графика, музыка и текстовые ресурсы

## Результат и границы доказательств

Для приложенного `SNAKE.GPF` восстановлены все **82 элемента** и алгоритм сжатия,
который **повторно создаёт все 269 593 байта архива** из распакованных ресурсов.
Повторная сборка не читает исходный GPF и не копирует сохранённые сжатые блоки.
Доступны две независимые реализации упаковщика: C89, совместимый с Borland C++,
и Python 3. Они используют одинаковый восстановленный алгоритм выбора совпадений.

SHA-256 оригинала и повторно собранного архива:

`f4cdf17fe0b0d2b6630b7dbb99c453469219dada00f89372530182809e8c7a68`

Все 94 потока LZSS распаковываются до ожидаемого размера и снова упаковываются
в первоначальные байты. Это 78 обычных файлов и 16 плоскостей четырёх экранов.
Графика извлечена в PNG без перерисовки: 54 растровых ресурса и 4 полноэкранных
изображения. Файлы PNG — визуальные производные; сборка использует оригинальные
распакованные плоскости, включая выравнивание и служебные байты.

Здесь «восстановлено» означает установленную структуру и исполняемую реализацию.
Названия полей, которыми не располагал исходный исполняемый файл, даны по смыслу.
Неустановленные поля явно отмечены. Равенство архива не доказывает совпадение
машинного кода C-реализации с оригинальным ассемблерным декодером.

Все адреса с пометкой **file** относятся к первоначальному `SNAKE.EXE`;
**image** означает смещение в MZ load image: `image = file - 0x1000`.
Адреса расшифрованного графического драйвера обозначены отдельно: они не являются
исходными байтами файла на диске.

## 2. Контейнер GAMOS PACKED FILE

Все многобайтные числовые поля GPF — little endian. Каталог расположен сразу
за заголовком. Его порядок значим для побайтового восстановления и сохранён.

### 2.1. Заголовок: 33 байта

| Смещение | Размер | Тип | Значение / смысл |
|---:|---:|---|---|
| `0x00` | 19 | bytes | `1A` + ASCII `GAMOS PACKED FILE` + `00` |
| `0x13` | 4 | bytes | `01 00 00 01`; отдельная семантика этих четырёх байтов не установлена |
| `0x17` | 2 | u16 LE | Число записей; здесь 82 (`52 00`) |
| `0x19` | 8 | bytes | Здесь нули; сохранены как резерв, назначение не установлено |

Значения `01 00 00 01` недостаточно, чтобы объявить конкретные поля версией,
числом томов или флагами. Из исследованного чтения достоверно следует только
размер заголовка и расположение счётчика записей.

Доказательство: функция **file `0x12DB6`** читает `0x21` байт в `DS:4104`.
Поиск **file `0x12E1D`** перемещается на смещение `0x21`, читает записи по `0x16`
байт и сравнивает счётчик цикла с `DS:411B`, то есть с `header + 0x17`.

### 2.2. Запись каталога: 22 байта

| Относительное смещение | Размер | Тип | Поле |
|---:|---:|---|---|
| `0x00` | 13 | char[13] | DOS-имя, завершённое нулём; оставшиеся байты сохранены |
| `0x0D` | 1 | u8 | Способ хранения: 1 или 2 в данном архиве |
| `0x0E` | 4 | u32 LE | Абсолютное смещение содержимого от начала GPF |
| `0x12` | 2 | u16 LE | Число хранимых байтов |
| `0x14` | 2 | u16 LE | Несжатый размер для способа 1; ноль для способа 2 |

Смещение записи `i`: `33 + 22*i`. Конец каталога:
`33 + 82*22 = 1837 = 0x072D`. Первый ресурс начинается именно там.
В данном файле записи описывают неперекрывающиеся, непрерывно следующие блоки;
нет промежутков между ними и нет хвоста после последнего блока.

Пример `PICKUP.BLO`, запись с индексом 1:

- имя `PICKUP.BLO`, способ 1;
- смещение `0x00000E1A` = 3610;
- упакованный размер 65, несжатый размер 160;
- данные занимают `[0xE1A, 0xE5B)`.

Поиск переводит запрошенное имя в верхний регистр перед сравнением с каталогом
(**file `0x1334B`**). Это поведение поиска, а не требование хранить имена в Unicode.

### 2.3. Способы хранения

**1 — отдельный поток LZSS.** В каталоге есть оба размера. Декодер получает
упакованную длину; отдельного маркера конца внутри потока нет.

**2 — четыре сжатые плоскости полного EGA-экрана.** Блок содержит четыре пары:
`u16 compressed_length` и следующие `compressed_length` байт LZSS.
Каждая плоскость распаковывается ровно в 28 000 байт. Полный ресурс — 112 000 байт.
Каталожный несжатый размер равен нулю, поскольку формат использует отдельный
путь обработки, а 112 000 не помещается в u16.

У исходного загрузчика есть и путь выдачи данных без распаковки, используемый
для получения блока способа 2 целиком. Значение способа 0 не встречается среди
82 записей; поддержка raw в утилите является отдельной возможностью реализации,
а не утверждением о наблюдавшихся ресурсах игры.

## 3. Алгоритм сжатия LZSS

### 3.1. Состояние

- кольцевой словарь: 4096 байт;
- начальная позиция записи: `0xFEE` = 4078;
- позиции `0..4077` перед каждым вызовом заполняются ASCII-пробелом `0x20`;
- последние 18 байт оригинальный декодер не очищает;
- длина совпадения: 3–18 байт;
- источник совпадения — абсолютный индекс в кольцевом словаре, не расстояние назад.

Ни один из 94 потоков не обращается к последним 18 неинициализированным байтам
раньше их записи в текущем вызове. Python-декодер дополнительно проверяет это.
Поэтому результат в данном наборе ресурсов не зависит от предыдущего вызова.

### 3.2. Флаги и токены

Перед группой до восьми токенов находится байт флагов. Биты используются от
младшего к старшему:

| Бит | Содержимое токена |
|---:|---|
| 1 | Один буквальный байт |
| 0 | Двухбайтовое описание совпадения |

Для совпадения сначала читается младший, затем старший байт слова `token`:

```c
source_index = token & 0x0FFF;
length       = (token >> 12) + 3;
```

Копирование выполняется последовательно через кольцевой словарь. Для каждого
байта источник читается **до** записи в текущую позицию словаря. Поэтому
самоперекрывающиеся совпадения корректны и позволяют, например, развернуть
длинную цепочку нулей. После каждого байта обе позиции маскируются `& 4095`.

Последняя группа может содержать меньше восьми токенов: окончание определяется
исчерпанием входной длины. Неиспользованные биты последнего флага не означают
дополнительных данных.

### 3.3. Проверка по оригинальному машинному коду

Декодер: **file `0x1438D..0x1441A`**, исходный **CS `1238:100D`**.

| Адрес file | Наблюдаемое действие |
|---:|---|
| `0x1439A` | Загрузка `CX=0xFEE` |
| `0x1439F` | `AL=0x20`, затем `REP STOSB`: инициализация словаря |
| `0x143B1` | Сдвиг флагов вправо |
| `0x143C0` | Проверка младшего бита флага |
| `0x143C6` | Ветвь буквального байта |
| `0x143E1` | Маска источника `0x0FFF` |
| `0x143E5..0x143F2` | Извлечение старшего полубайта и прибавление 3 |
| `0x143F5..0x1440A` | Последовательное копирование совпадения со сворачиванием индексов |

Программный декодер расположен в `src/gpfcodec.c`; вариант Python — в `tools/gpf.py`.

### 3.4. Почему обычного LZSS-упаковщика недостаточно для точного совпадения

Один и тот же несжатый массив можно представить множеством корректных потоков.
Для этого файла восстановлен также **детерминированный выбор совпадения**:
упорядоченные бинарные деревья по первому байту, окно 4096, максимальная длина 18,
вставка начальных узлов в порядке `r-1`…`r-18`, выбор только строго более длинного
совпадения и замена узла при полном совпадении длины 18.

Эти детали определяют, на какую из нескольких равных последовательностей
сошлётся упаковщик. Здесь такой алгоритм даёт точное совпадение всех потоков.
В проекте не хранится «карта исходных токенов» для подстановки результата.

## 4. Полноэкранные ресурсы: способ 2

Размер экрана: **640 × 350**, четыре бита на пиксель, 16 индексов цвета.
Каждая плоскость содержит 350 строк по 80 байт; старший бит байта соответствует
левому пикселю из восьми. Заголовка `.BLO` внутри распакованного экрана нет.

| Порядок блока | Цветовой бит | Значение при установленном пикселе |
|---:|---:|---:|
| 0 | 0 | 1 |
| 1 | 1 | 2 |
| 2 | 2 | 4 |
| 3 | 3 | 8 |

Это подтверждает экранная функция **file `0x132AA..0x1334A`**: цикл из четырёх
итераций устанавливает EGA map mask `1 << plane` через `0x3C4/0x3C5`, читает длину
очередного блока и распаковывает его в видеопамять. Поэтому способ 2 удобно
распаковывать по одной плоскости даже в 16-битном C: массив на 112 КБ не нужен.

| Ресурс | Упакованные длины плоскостей | Общий размер блока |
|---|---|---:|
| `PLAN1.BLO` | 9515, 9488, 10138, 11376 | 40525 |
| `PLAN3.BLO` | 3576, 3612, 3601, 3872 | 14669 |
| `PLAN2.BLO` | 7511, 7538, 7556, 9204 | 31817 |
| `RPLAN2.BLO` | 7493, 7499, 7514, 9167 | 31681 |

Каждый общий размер включает четыре двухбайтовых префикса длин.

## 5. Обычные `.BLO`: дескриптор и плоскости

### 5.1. Расположение

У всех 54 обычных `.BLO` есть 16-байтовый дескриптор изображения, затем 16
сохраняемых байтов, затем четыре плоскости. Начало каждой плоскости выровнено
на 16 байт. Размер строки выровнен на слово, а не только на байт.

| Смещение | Размер | Смысл |
|---:|---:|---|
| `0x00` | 2 | Ширина в пикселях |
| `0x02` | 2 | Высота в пикселях |
| `0x04` | 2 | Шаг строки в байтах |
| `0x06` | 1 | Упакованные свойства дескриптора; в файлах `0x18` |
| `0x07` | 1 | Дополнительное байтовое смещение начала растровых данных; здесь 0 |
| `0x08` | 8 | Четыре u16-смещения плоскостей в параграфах по 16 байт |
| `0x10` | 16 | Сохранённый хвост заголовочной области; устойчивое файловое назначение не установлено |
| далее | переменно | Четыре плоскости с выравниванием |

Для встречающихся файлов:

```text
stride          = 2 * ceil(width / 16)
plane_bytes     = stride * height
plane_allocated = 16 * ceil(plane_bytes / 16)
file_size       = 32 + 4 * plane_allocated
plane_offset[p] = 32 + p * plane_allocated
```

Часть хвостовых байтов выглядит как состояние/остаточные данные создавшего файл
инструмента; у `LETTER.BLO` есть отличающиеся ненулевые значения. Их происхождение
не доказано. Удалять их или обнулять при побайтовой реконструкции нельзя.
Для чтения пикселей из данных этого архива они не нужны.

### 5.2. Свойства дескриптора

Создание дескриптора восстановлено в расшифрованном драйвере, **file-equivalent
`0x128C6..0x12958`**, относительная функция драйвера `0x2B60`.

- `flags & 7`: горизонтальное смещение первого пикселя внутри байта;
- `(flags >> 3) & 3`: число цветовых плоскостей минус один;
- бит `0x40`: дополнительная плоскость/режим маски;
- бит `0x80`: выбор пути для аппаратной EGA-памяти;
- бит `0x20` в обнаруженном конструкторе не устанавливается.

В исследуемых файловых ресурсах всегда `flags = 0x18`: четыре обычные плоскости,
нулевое битовое смещение, без дополнительной маски. Поддержка произвольных иных
режимов драйвера требует отдельной проверки; документация не объявляет их
полностью исследованными только по конструктору.

При работе в памяти слова `plane_offset` преобразуются в реальные сегментные
адреса. В файле сохранены относительные параграфы. Нельзя интерпретировать
исходное значение `2` как смещение на два байта.

### 5.3. Важное отличие: порядок плоскостей противоположен полноэкранному

**У обычного `.BLO` первая плоскость даёт бит 3 цвета, последняя — бит 0.**

```python
pixel = 0
for plane in range(4):
    byte = data[plane_offset[plane] + y * stride + x // 8]
    pixel = (pixel << 1) | ((byte >> (7 - x % 8)) & 1)
```

| Порядок плоскости | Вес цвета для обычного `.BLO` | Вес для полноэкранного способа 2 |
|---:|---:|---:|
| 0 | 8 | 1 |
| 1 | 4 | 2 |
| 2 | 2 | 4 |
| 3 | 1 | 8 |

Это установлено по функции чтения пикселя оригинального расшифрованного драйвера
**file-equivalent `0x127DA`**, относительное смещение `0x2A74`, и проверено её
выполнением в Unicorn. Например, у `BODYALL.BLO` пиксель `(1,0)` имеет биты
плоскостей `[1,0,0,0]`; оригинальная функция возвращает **8**, а не 1.
Код `gpf_blo_pixel` в C повторяет этот порядок.

PNG используют стандартную 16-цветную EGA-палитру и сохраняют исходные пиксели.
Это извлечение изображений; реальный видеорежим и динамическая смена палитры
полной игры не запускались в рамках этой проверки ресурса.

## 6. `.SND`: банки инструментов AdLib

Эти файлы содержат определения инструментов FM-синтезатора, а не PCM-звук.
Структура соответствует раннему банку тембров AdLib; названия параметров
сопоставлены с независимой реализацией [AdPlug mus.cpp](https://github.com/adplug/adplug/blob/master/src/mus.cpp)
и [composer.cpp](https://github.com/adplug/adplug/blob/master/src/composer.cpp).
Размеры, имена и значения прочитаны из ресурсов игры.

### 6.1. Заголовок и массивы

| Смещение | Тип | Смысл |
|---:|---|---|
| 0 | u8 | Старшая версия: 1 |
| 1 | u8 | Младшая версия: 0 |
| 2 | u16 LE | Число инструментов `N` |
| 4 | u16 LE | Смещение массива определений: `6 + 9*N` |
| 6 | char[N][9] | Имена, до 8 символов и нуль |
| `6+9*N` | u16[N][28] | Определения: 56 байт на инструмент |

Всегда выполняется `file_size = 6 + 9*N + 56*N = 6 + 65*N`.
Например, `MUS1.SND`: 7 инструментов, определения с 69-го байта,
полный размер 461 байт.

### 6.2. Определение инструмента

Первые 13 слов описывают модулятор, следующие 13 — несущий оператор; последние
два слова — формы волн модулятора и несущего. Порядок слов каждого оператора:

| Индекс | Параметр |
|---:|---|
| 0 | key scale level |
| 1 | frequency multiplier |
| 2 | feedback |
| 3 | attack rate |
| 4 | sustain level |
| 5 | sustaining sound |
| 6 | decay rate |
| 7 | release rate |
| 8 | output level |
| 9 | amplitude vibrato |
| 10 | frequency vibrato |
| 11 | envelope scaling |
| 12 | FM/connection selector |

Хранить нужно полные 16 бит, включая необычные значения. Например, в некоторых
словах присутствует `0xFFF6`. Нельзя автоматически «исправлять» их до диапазона
регистра OPL: файловое представление и последующее использование драйвером —
разные уровни. Полные определения выгружены в `analysis/gpf-metadata/*.SND.json`.

## 7. `.MUS`: последовательности AdLib

Это **AdLib MUS 1.0**, а не одноимённый формат Doom.
Заголовок — 70 байт; после него идут события с задержками и MIDI-подобными
командами. Патчи адресуют инструмент из соответствующего `.SND`.

### 7.1. Заголовок

| Смещение | Тип | Смысл |
|---:|---|---|
| 0 | u8 | majorVersion = 1 |
| 1 | u8 | minorVersion = 0 |
| 2 | u32 LE | tuneId, здесь 0 |
| 6 | char[30] | Название, здесь пустое |
| 36 | u8 | tickBeat, здесь 240 |
| 37 | u8 | beatMeasure, здесь 4 |
| 38 | u32 LE | Заявленное число тиков |
| 42 | u32 LE | Размер событийной части |
| 46 | u32 LE | Заявленное число команд |
| 50 | bytes[8] | Резерв |
| 58 | u8 | Режим звучания |
| 59 | u8 | Диапазон pitch bend |
| 60 | u16 LE | Основной темп |
| 62 | bytes[8] | Резерв |
| 70 | bytes[dataSize] | События |

У всех семи файлов `70 + dataSize` точно равно размеру файла.

### 7.2. События

Каждое событие начинается с задержки. Байт `F8` добавляет 240 тиков; после цепочки
таких байтов читается завершающая однобайтовая часть задержки. Это не MIDI VLQ.
Затем следует команда либо данные с ранее установленным running status.

| Старший полубайт / команда | Данных | Смысл |
|---|---:|---|
| `8n` | 2 | Выключение ноты |
| `9n` | 2 | Нота и громкость; нулевая громкость выключает ноту |
| `An` | 1 | Изменение громкости; здесь один байт, в отличие от MIDI polyphonic key pressure |
| `Bn` | 2 | Контроллер и значение |
| `Cn` | 1 | Номер инструмента |
| `Dn` | 1 | Channel pressure |
| `En` | 2 | Pitch bend |
| `F0 ... F7` | переменно | System exclusive; в ресурсах есть управление темпом |
| `FC` | 0 | Конец композиции |

Для темпа встречается последовательность `F0 7F 00 integer fraction F7`, которая
задаёт множитель основного темпа `integer + fraction/128`.

Парсер в `tools/gpf_meta.py` проходит все события до конца и сохраняет адреса,
накопленные тики и явность running status. Он не синтезирует звук.

### 7.3. Несовпадения деклараций, которые нельзя скрывать

| Композиция | Команды в заголовке | Разобранные события | Тики в заголовке | Тики по потоку |
|---|---:|---:|---:|---:|
| `MOOD.MUS` | 1092 | 1075 | 17880 | 17880 |
| `MUS1.MUS` | 153 | 153 | 7680 | 7680 |
| `MUS2.MUS` | 1948 | 1947 | 42000 | 42240 |
| `MUS3.MUS` | 1019 | 1019 | 11520 | 11520 |

В `MUS2` реальный поток по принятому правилу задержек содержит на 240 тиков больше
декларации. В `MOOD` счётчик команд также не совпадает. В сборке эти поля сохранены
неизменными; причина расхождений не доказана. Они могут относиться к генератору
композиций либо к способу учёта служебных событий. Разбор потока и равенство
после перепаковки не требуют изменения этих деклараций.

Дубли по несжатым байтам:

- `SN_TITL.MUS/SND` равны `MUS1.MUS/SND`;
- `SN_GAME.MUS/SND` равны `MUS2.MUS/SND`;
- `SN_BATT.MUS/SND` равны `MUS3.MUS/SND`.

## 8. `.MID`: стандартные MIDI-файлы

Три файла имеют обычную структуру SMF:

- `MThd`, big-endian длина 6;
- format 0, один трек, division 480;
- `MTrk`, big-endian длина данных;
- события с MIDI VLQ-задержками, channel status/running status, meta и SysEx.

`MUS1.MID`: 44 146 байт; `MUS2.MID`: 36 433; `MUS3.MID`: 15 857.
В отличие от внешнего GPF, числовые поля заголовков SMF имеют big-endian порядок.
Все три трека структурно разобраны до объявленного конца. События доступны в
`analysis/gpf-metadata/*.MID.json`; исходные MIDI можно открыть отдельно от игры.

Подмножество MIDI, реализованное именно в этом EXE, внутренние команды
SysEx `7D`, 30-байтовые инструменты, hooks и состояния секвенсора подробно
описаны в [MIDI_INTERNALS.md](MIDI_INTERNALS.md). Там отдельно отмечены
ограниченный running status и сохранённые необычные ветви исходного драйвера.

## 9. Тексты и локализация

`ENGLISH.TXT`, `RUSSIAN.TXT`, `SWEDEN.TXT` — байтовые DOS-тексты с CRLF.
Для русского текста требуется CP866, а не Windows-1251 и не UTF-8.
Первые шесть строк — клавиатурные/символьные таблицы; далее идут позиционно
адресуемые подписи интерфейса, сообщения и титры. Это не словарь ключ=значение.
Порядок строк является частью формата.

Варианты `RUSINSTR.TXT` и `ENGINSTR.TXT` содержат пользовательские инструкции.
Ресурсы заканчиваются служебными строками/пустыми строками и DOS EOF `0x1A`.
Эти байты сохраняются. Простое открытие и пересохранение UTF-8-редактором с
нормализацией переводов строк изменит ресурс и нарушит точное совпадение.

В `analysis/gpf-metadata/` есть UTF-8-копии для чтения и JSON с индексом каждой
строки. Они не заменяют байтовые файлы в `assets/resources/` при сборке.

## 10. `PASSW.RUS` / `PASSW.ENG`

Это таблицы слов для экранной проверки по координатам, связанные с печатной
сеткой. Они отделены от паролей отдельных змей `.SNK`.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 2 | Число записей: 100 |
| `2+18*i` | 1 | Буква колонки: ASCII `A`…`E` |
| `3+18*i` | 1 | Номер строки: 1…20 |
| `4+18*i` | 16 | Накопительно XOR-кодированное слово |

Полный размер: `2 + 100*18 = 1802` байта.

Алгоритм декодирования записи:

```python
previous = column_byte ^ row_byte
for encoded in record[2:18]:
    decoded.append(encoded ^ previous)
    previous = encoded
```

Результат — пятибуквенное слово, повторённое три раза, и нулевой байт.
Например, английская клетка A1 содержит `JELLYJELLYJELLY\0`, русская —
`СЦЕНАСЦЕНАСЦЕНА\0` в CP866.

Подтверждающий код выбора записи: **image `0xC6D1` / `0xC721`**;
формирование повторения и сравнение: **image `0xC7A2..0xC7F7`**
(для file-адресов прибавить `0x1000`). Полные таблицы в JSON созданы для изучения
содержимого ресурсов. В исполняемом файле проверка не отключалась.

## 11. Сборка и воспроизведение проверок

### C89 / Borland C++ large model

В пакете сохранены результаты реальной DOS-сборки Borland C++ 3.1:
[лог компилятора](../build/dos/GPFTEST.LOG),
[проверка 82 ресурсов и 94 потоков](../build/dos/GPFTEST.OUT),
[вывод сборщика GPF](../build/dos/GPFBUILD.OUT) и
[повторно собранный архив](../build/dos/rebuilt/SNAKE.GPF).
Полные параметры использованной сборки находятся в
[BUILD.BAT](../build/dos/BUILD.BAT). Ниже приведены отдельные команды для инструментов.

Из каталога `src`:

```bat
bcc -ml -egpftest.exe gpftest.c gpfcodec.c
bcc -ml -egpfbuild.exe gpfbuild.c gpfcodec.c
bcc -ml -DGPF_STANDALONE -egpfcodec.exe gpfcodec.c
```

Проверка 94 исходных потоков:

```bat
gpftest ..\original\SNAKE.GPF
```

Повторная сборка всего GPF из распакованных ресурсов:

```bat
gpfbuild ..\assets\resources ..\build\SNAKE.GPF
```

Извлечение отдельного ресурса:

```bat
gpfcodec ..\original\SNAKE.GPF BODYALL.BLO BODYALL.BLO
```

Для GCC те же исходники собираются в строгом C89:

```sh
gcc -std=c89 -pedantic -Wall -Wextra -Werror src/gpftest.c src/gpfcodec.c -o gpftest
gcc -std=c89 -pedantic -Wall -Wextra -Werror src/gpfbuild.c src/gpfcodec.c -o gpfbuild
```

Код явно разбирает числа и не зависит от выравнивания C-структур. В DOS используются
16-битные длины блоков и отдельные буферы плоскостей; словарь и дерево совпадений
выделяются в heap, чтобы не переполнять обычный DOS stack.

### Python 3

Из корня проекта:

```sh
python3 tools/gpf.py unpack original/SNAKE.GPF assets
python3 tools/gpf.py pack assets/gpf_manifest.json build/SNAKE.GPF
python3 tools/gpf.py verify original/SNAKE.GPF assets/gpf_manifest.json
python3 tools/gpf.py render assets/gpf_manifest.json assets/png
python3 tools/gpf_meta.py assets/resources analysis/gpf-metadata
```

Pillow нужен только для `render`. Сам контейнер, LZSS, перепаковка и разбор
семантических ресурсов используют стандартную библиотеку Python.

## 12. Остаточные неизвестные

1. Точное назначение четырёх байтов заголовка GPF `0x13..0x16` и резервного хвоста:
   их значения в единственном исследованном контейнере не позволяют различить
   возможные назначения.
2. Происхождение неодинаковых 16 байт заголовочной области обычных `.BLO`:
   значения сохранены, но для чтения пикселей не нужны; поведение исходного
   инструмента, записавшего их, не установлено.
3. Полная спецификация неиспользуемых в этих ресурсах режимов маски/видеопамяти
   графического дескриптора: все файловые образцы имеют `flags = 0x18`, поэтому
   они не проверяют остальные варианты.
4. Причина расхождения счётчиков отдельных `.MUS` с событийным потоком:
   расхождения измерены, но принятую авторским генератором систему подсчёта
   эти данные однозначно не определяют.
5. Синтез звука и соответствие конкретному аппаратному драйверу здесь не проверялись:
   выполнен структурный разбор событий и инструментов, без проверки итогового
   звукового сигнала на соответствующем устройстве.

Эти неизвестные не мешают извлечению всех данных, правильному чтению пикселей
исследованных изображений и доказанной побайтовой повторной сборке GPF.
