# Форматы Snake Battle: `.SNK` и `.REC`

## 1. Объект исследования и проверенный результат

Спецификация восстановлена по поставленному `SNAKE.EXE`, 15 файлам `.SNK` и 5 файлам `.REC`. SHA-256 исследованного EXE:

```text
c4e064a1cf15e438017d4d6443817424f816ce4b749fcc279f2d97dc7bd86821
```

Для каждого из 20 файлов выполнено **структурное чтение и обратная запись с точным совпадением всех байтов**. Проверены две независимые реализации: Python и C89. В дополнение обе исходные процедуры XOR исполнены непосредственно из EXE в эмуляторе x86-16 Unicorn: 128 наборов входов на процедуру, всего 256 вызовов, совпадают изменённый буфер и возвращаемое значение. Это проверка процедур, а не запуск DOS-интерфейса игры.

Восстановленный C-код также реально скомпилирован **Borland C++ 3.1** под DOS. Для трёх полных процедур — кодирования XOR, декодирования XOR и преобразования пароля — получено **точное совпадение всех 146 байтов машинного кода** с исходным EXE. Сравнение прямое, без маскирования адресов или исправления скомпилированного результата.

### Система адресов доказательств

В исследованном EXE заголовок MZ занимает `0x1000` байт. Адреса `CS:IP` ниже заданы относительно загрузочного образа, до прибавления сегмента загрузки DOS:

```text
image_offset = CS * 16 + IP
file_offset  = 0x1000 + image_offset
```

Обозначения `[E01]`–`[E21]` ссылаются на подписанные участки в `analysis/snk_rec_evidence.txt`. Для данных базовый сегмент DGROUP равен `1679h`; например, `DS:04B7` находится в файле по адресу `0x17C47`.

## 2. Общий алгоритм накопительного XOR

SNK целиком, кроме первого и последнего байта, кодируется накопительным XOR. В REC этим способом кодируется только начальная таблица участников.

Пусть `S` — открытый начальный байт, `P[i]` — открытый текст, `C[i]` — хранимый кодированный байт. Тогда:

```text
C[-1] = S
C[i]  = P[i] XOR C[i-1]
P[i]  = C[i] XOR C[i-1]
```

При декодировании предыдущий **кодированный** байт необходимо сохранить до изменения текущего. XOR с постоянным ключом или с предыдущим открытым байтом даст другой результат.

Восстановленный эквивалент двух исходных процедур:

```c
unsigned char far snk_encode(unsigned char far *p,
                             int length, unsigned char seed)
{
    int i;
    unsigned char previous;
    previous = seed;
    for (i = 0; i < length; i++) {
        *p ^= previous;
        previous = *p;
        p++;
    }
    return previous;
}

unsigned char far snk_decode(unsigned char far *p,
                             int length, unsigned char seed)
{
    int i;
    unsigned char previous;
    unsigned char temporary;
    previous = seed;
    for (i = 0; i < length; i++) {
        temporary = previous;
        previous = *p;
        *p ^= temporary;
        p++;
    }
    return previous;
}
```

Первая процедура расположена в `0B2B:000F`, физический адрес `0xC2BF`, длина 55 байт `[E01]`; вторая — в `0B2B:0046`, физический адрес `0xC2F6`, длина 61 байт `[E02]`. В исходнике EXE длина — знаковый 16-битный `int`, указатель — дальний, возврат байта происходит через `AL`. При нулевой длине обе процедуры возвращают `seed`. Увеличивается только 16-битное смещение дальнего указателя; нормальные блоки SNK длиной до 1473 байт не требуют перехода через границу сегмента.

Штатное сохранение выбирает `seed = random(128)`: нормальный диапазон создаваемого игрой ключа `00h`–`7Fh`. Сам алгоритм определён для всех 256 значений; проверка исходных процедур включает весь байтовый диапазон случайных входов. Формат не содержит криптографической защиты.

## 3. Файл `.SNK`

### 3.1. Внешняя структура

| Смещение в файле | Размер | Содержание |
|---:|---:|---|
| `0` | 1 | Начальный байт XOR `seed` |
| `1` | 105 | Кодированный паспорт змеи |
| `106` | `152 × N` | Кодированные карты, без перезапуска состояния XOR |
| `106 + 152 × N` | 1 | Повтор последнего кодированного байта |

`N` хранится в расшифрованном паспорте. Нормальный диапазон `1..9`. Полный размер:

```text
SNK_size = 107 + 152 * N
```

Возможные размеры штатных файлов: 259, 411, 563, 715, 867, 1019, 1171, 1323 и 1475 байт. Отдельной ASCII-сигнатуры нет. Расшифрованное поле версии равно единице.

Последний байт иногда удобно назвать контрольным, но проверка игры сравнивает его **только с последним кодированным байтом**. Это не CRC всего файла. Повреждение более раннего кодированного байта способно изменить два соседних расшифрованных байта и пройти эту проверку. Код сравнения находится в `0B33:0BE4` и следующем блоке `[E04]`.

Исходный загрузчик `0B33:0A4C` сначала читает и декодирует 105 байт, проверяет версию, вычисляет размер, возвращается в начало файла и читает полный блок `[E04]`. Формула размера в машинном коде:

```text
0x5C1 - (9 - N) * 0x98 = 105 + N * 152
```

Для недопустимого количества карт исходный загрузчик временно подставляет `N=1` при расчёте размера. Восстановленные библиотечные API отвергают такое значение: сохранение штатных входов остаётся точным, а обработка повреждённых файлов сделана явной.

Исходный сохранитель `0B33:0C6B` записывает seed, кодирует блок прямо в памяти, записывает его, затем декодирует тот же блок обратно и записывает последний кодированный байт `[E05]`. C-реализация сохраняет это свойство: `snk_write` возвращает переданную структуру в открытый вид даже после ошибки записи кодированного блока.

### 3.2. Паспорт: 105 байт

Смещения этой таблицы отсчитываются **от первого расшифрованного байта паспорта**, без seed. В SNK соответствующее физическое смещение на единицу больше. Все 16-битные поля хранятся в little-endian. В строках используется однобайтовая DOS-кодировка; для содержимого поставки подходит CP866.

| Смещение | Hex | Размер | Восстановленное поле | Значение |
|---:|---:|---:|---|---|
| 0 | `00` | 2 | `version` | Версия структуры, `1` |
| 2 | `02` | 2 | `editor_level` | `0` новичок, `1` любитель/advanced, `2` эксперт |
| 4 | `04` | 2 | `card_count` | Количество карт `1..9` |
| 6 | `06` | 2 | `battle_count` | Число завершённых боёв/раундов |
| 8 | `08` | 2 | `rating` | Рейтинг, исходное значение 1000 |
| 10 | `0A` | 11 | `password` | Дополнительно преобразованная строка, до 10 символов и NUL |
| 21 | `15` | 9 | `name` | Имя, до 8 символов и NUL |
| 30 | `1E` | 10 | `date` | Текстовая дата, в поставке `dd.mm.yy` |
| 40 | `28` | 21 | `comments[0]` | Первая строка, до 20 символов и NUL |
| 61 | `3D` | 21 | `comments[1]` | Вторая строка |
| 82 | `52` | 21 | `comments[2]` | Третья строка |
| 103 | `67` | 2 | `color` | Индекс варианта окраски змеи |

Поля интерпретируются восстановленными инструментами как беззнаковые 16-битные значения для сохранения всех комбинаций битов. Оригинальный 16-битный C-код для сравнений и арифметики часто использует знаковый `int`. Для нормальных значений поставки это различие не меняет результатов. Координаты карт, напротив, явно представлены знаковыми 16-битными числами.

Индекс `color` не следует ограничивать числом 15: в поставке встречаются 16 и 19. Это индекс варианта окраски/спрайта, а не непосредственный номер одного пикселя EGA. RGB-значения палитры в самом SNK отсутствуют.

Пустое имя не означает отсутствие участника. В REC существуют полноценные записи участников с пустым полем имени.

### 3.3. Пароль и неиспользованные байты строк

Кроме общего XOR, пароль преобразуется отдельной процедурой `044D:022F`, физический адрес `0x56FF` `[E03]`. До первого NUL каждый байт заменяется на `255 - byte`. Нулевой терминатор и всё после него остаются без изменений. Повтор того же преобразования восстанавливает строку. Остальные строковые поля этого дополнительного преобразования не имеют.

После первого NUL может оставаться старая информация редактора. Такие байты **не являются гарантированным нулевым заполнением**. Например, некоторые паспорта содержат пустую текущую строку и ненулевой хвост от прежнего значения. Полное обнуление «неиспользованного» хвоста уничтожает побайтовую идентичность.

Поэтому JSON хранит строку так:

```json
{
  "text": "TEST",
  "after_text_hex": "0000000000"
}
```

`after_text_hex` включает терминатор и все оставшиеся байты поля. Для пароля поле `text` уже содержит результат обратного дополнения, а хвост хранит точные исходные байты. При изменении длины `text` следует удалить `after_text_hex`, чтобы сборщик создал новое нулевое заполнение. Иначе проверка ширины обнаружит несоответствие. Поля не преобразуются в Unicode внутри двоичного формата; UTF-8 используется только для JSON.

Ещё одно различие между архивным чтением и загрузкой в игру: после успешного чтения исходная программа заменяет поле `name` именем загруженного файла без расширения, `0B33:0C48` и далее `[E04]`. Архивный декодер этого не делает, поскольку такая замена могла бы изменить исходные байты.

### 3.4. Число боёв и рейтинг

Поле `+6` имеет подтверждённый смысл, а не угадано по значениям. В `0729:2C13` значение счётчика раундов текущей сессии `DS:340D` прибавляется к `header+6`. Дальше обновляется рейтинг по накопленному результату сессии `[E18]`.

Если `R` — число раундов сессии, `S` — суммарный результат змеи за сессию, `B` — прежнее число раундов в паспорте, то наблюдаемая арифметика такова:

```text
B_new = B + R
delta = S - 10 * R
step  = delta / B_new       # знаковое целочисленное деление к нулю
if step == 0 and delta != 0:
    step = +1 if delta > 0 else -1
rating_new = rating_old + step
```

Эта формула объясняет назначение обоих полей. Здесь не моделируется переполнение исходного 16-битного `int` на искусственно больших значениях.

### 3.5. Карта поведения: 152 байта

Первая карта следует сразу после паспорта, по смещению 105 открытого блока, то есть по физическому смещению 106 файла. Между картами нет указателей, длин и выравнивающих байтов.

| Смещение в карте | Размер | Поле |
|---:|---:|---|
| 0 | 1 | Группа рамки карты, выбирающая внешний AND/OR |
| 1 | 2 | Знаковая координата головы `head_x` |
| 3 | 2 | Знаковая координата головы `head_y` |
| 5 | 147 | Матрица 7×7; три байта на клетку |

Для нормальной карты координаты находятся в диапазоне `0..6`. Матрица записана **по столбцам**: внешний индекс `x`, внутренний `y`. Адрес тройки:

```text
card_offset(x, y) = 5 + 21*x + 3*y
```

Тройка клетки имеет следующий вид:

| Байт | Значение |
|---:|---|
| `+0` | Номер цветовой логической группы `0..4` |
| `+1` | Флаг отрицания; штатные значения `0` и `1` |
| `+2` | Код элемента карты |

Коды элементов:

| Код | Значение в сопоставлении |
|---:|---|
| 0 | Пустая клетка |
| 1 | Стена/препятствие |
| 2 | Значение редакторского шаблона; точное назначение UI не установлено |
| 3 | Хвост чужой змеи |
| 4 | Хвост своей змеи |
| 5 | Тело чужой змеи |
| 6 | Тело своей змеи |
| 7 | Голова чужой змеи |
| 8 | Голова своей змеи, якорь карты; пропускается сопоставителем |
| 9 | Неограниченная клетка, wildcard; пропускается сопоставителем |

Код 2 нельзя объявлять пустотой: исходный сопоставитель сравнивает его как обычное буквальное значение; очистка игрового поля записывает код 0. В данной поставке значение 2 обнаружено в начальном редакторском шаблоне. Семантика соответствующего значка требует отдельного исследования интерфейса.

Общая таблица логики групп хранится в `DS:04B7` `[E21]`:

| Группа | Логика |
|---:|---|
| 0 | AND |
| 1 | OR |
| 2 | OR |
| 3 | AND |
| 4 | AND |

Эта же таблица применяется к байту рамки карты. Цветовая группа является номером логического класса; названия видимых цветов не нужны для восстановления файла и здесь не подменяются догадками о палитре.

Исходный сопоставитель `0729:1058` пропускает коды 8 и 9, для остальных клеток вычисляет `(observed_tile == rule_tile) XOR negate`. В AND-группе неуспешная клетка обнуляет результат всей группы. В OR-группе учитываются совпавшие клетки. Рамка AND требует ненулевого результата каждой участвующей группы; рамка OR допускает совпавшие группы. Итог содержит и флаг совпадения, и число учитываемых совпадений: последнее используется для сравнения альтернатив. Пустая карта, не содержащая проверяемых клеток, совпадает с оценкой ноль. Полный восстановленный алгоритм находится в `src/logic.c`.

Карта привязывается к реальной голове координатами `head_x/head_y`, а не всегда геометрическим центром. Игра рассматривает её повороты и отражение:

```text
Отражение по X:
    head_x' = 6 - head_x
    cell'[x][y] = cell[6-x][y]

Поворот по часовой стрелке:
    head_x' = 6 - head_y
    head_y' = head_x
    cell'[6-y][x] = cell[x][y]
```

Доказательства преобразований: `0729:000D` и `0729:00B4`; размер копируемой карты `0x98`. Собственная/чужая принадлежность устанавливается при построении обзора: игровые коды хвоста, тела и головы равны 4, 6, 8; если владелец иной, код уменьшается на единицу. Подробные дифференциальные проверки этих процедур входят в материалы восстановления игровой логики.

### 3.6. Конкретный пример: `TEST.SNK`

`TEST.SNK` имеет размер 259 байт и одну карту. Seed равен `68h`, версия 1, уровень 0, число боёв 0, рейтинг 1000, дата `16.12.94`, индекс окраски 6. Первые байты:

```text
Открытый паспорт: 01 00 00 00 01 00 00 00 E8 03 DF 00 00 00 00 00
Кодированный:    69 69 69 69 68 68 68 68 80 83 5C 5C 5C 5C 5C 5C
```

Например, первый байт `01 XOR 68 = 69`; второй `00 XOR 69 = 69`. Конечный контрольный байт файла равен `4Ch`.

В карте рамка имеет группу 0, голова находится в `(3,3)`. Клетка `(3,2)` содержит `{group:3, negate:0, tile:3}`, то есть условие чужого хвоста перед головой. Клетка `(3,3)` содержит код 8. Остальные 47 клеток имеют код 9. Этот пример проверяет не только длину блока: он демонстрирует оси матрицы, якорь, тройки правил и смысл кода 3.

## 4. Файл записи `.REC`

### 4.1. Переключение двух разных режимов хранения

REC не является зашифрованным снимком поля. В нём сохранены паспорта участников и поток решений, достаточный для исходной игры, чтобы повторить движение. Карты поведения в REC отсутствуют.

| Часть | Представление |
|---|---|
| Первый байт | Открытый XOR seed |
| Таблица участников и её терминатор | Накопительный XOR из раздела 2 |
| Поток воспроизведения | Открытые четырёхбитные значения, старшая половина байта первой |
| Возможный хвост после окончания | Старое содержимое ранее более длинной записи |

Ключевая граница доказана исходным вызовом `0E92:00F8`: он включает упакованный режим, сбрасывает фазу полубайта и буфер `[E08, E12]`. **После этой границы XOR не применяется.** Попытка расшифровать REC целиком даёт ложную структуру потока.

### 4.2. Таблица участников

После seed в одном непрерывном XOR-потоке записываются:

```text
slot:u8 + snake_header:105 bytes
slot:u8 + snake_header:105 bytes
...
0x0C:u8
```

`slot` — номер участника `0..3`, а `snake_header` имеет точную структуру 105-байтового паспорта SNK. Нет списка карт после него, даже если поле `card_count` паспорта ненулевое. Указатель присутствия участника определяется наличием записи slot. Поле имени может быть пустым.

Исходный писатель перечисляет присутствующих участников по возрастающему slot. Восстановленный JSON дополнительно сохраняет порядок записей, чтобы обратная запись не требовала сортировки. Номер участника не может повторяться в нормальной таблице.

Если записано `K` участников, начало полубайтового потока находится по смещению:

```text
packed_stream_offset = 1 + K*(1+105) + 1 = 2 + 106*K
```

Во всех пяти поставленных REC `K=4`, поэтому граница равна **426 байтам, `0x1AA`**. Читатель таблицы — участок `0729:24F3`, писатель — `0729:2577` `[E12]`.

### 4.3. Порядок полубайтов и значения

Каждый байт `ABh` представляет сначала токен `Ah`, затем токен `Bh`. Между токенами одного события выравнивания по байту нет. Поэтому `0xE` может находиться в младшей половине байта, а следующий байт результата начинаться с полубайта следующего физического байта.

| Токен | Значение |
|---:|---|
| `0..3` | Номер выбранной змеи либо направление; смысл определяется состоянием игрового алгоритма |
| `0xE` | Конец раунда; далее результаты присутствующих участников |
| `0xD` | Конец воспроизведения |
| `4..0xC`, `0xF` | Отдельные штатные события с такими кодами в исследованных потоках не обнаружены |

`0xC` служит терминатором только в **байтовом XOR-заголовке**. Его нельзя автоматически переносить в набор полубайтовых событий.

Для направления соответствие: `0` вверх, `1` вправо, `2` вниз, `3` влево. Для номера змеи это просто slot из заголовка. Процедура выбора следующего участника `0729:0F27` читает/записывает один токен `[E14]`; процедура выбора хода `0729:143C` читает/записывает направление `[E15, E16]`.

Последовательность нельзя безусловно делить на пары «змея, направление»: когда змее некуда ходить, процедура завершает обработку без записи направления. Чтобы присвоить каждому токену 0..3 роль и номер хода, необходимо воспроизводить состояние поля. Форматный декодер честно сохраняет такие участки как список `decisions.tokens`, без выдуманных пар. Это не мешает точному восстановлению хранения и разбору результатов.

### 4.4. Результаты раунда

После токена `0xE` идут **по два байта на каждого присутствующего участника**, в порядке slot `0,1,2,3` с пропуском отсутствующих. Эти байты также передаются через полубайтовый канал. Для одного результата получается четыре токена:

```text
score = low_byte + 256*high_byte
tokens = low_byte >> 4, low_byte & 15, high_byte >> 4, high_byte & 15
```

Пример: результат 31 имеет байты `1F 00` и токены `1,F,0,0`. Здесь `F` — часть результата, а не неизвестное событие. Поэтому сканирование всех полубайтов с поиском маркеров без учёта длины результата неправильно.

Писатель результатов расположен в `0729:04CC`, читатель — в `0729:046E` `[E13]`. Оба обходят четыре возможных слота и читают/пишут ровно два байта для присутствующего участника. Для четырёх участников один блок результата занимает `1+16=17` токенов, включая маркер E.

Результаты в поставке неотрицательны и суммируются в 40. В файле хранится обычное 16-битное слово, без отдельного кода знака, десятичного представления или общего результата раунда.

### 4.5. Конец записи, заполнение и остатки предыдущего файла

В конце исходная игра явно записывает **два токена D**, затем закрывает файл `[E19]`. Если второй D оказался в старшей половине байта, процедура закрытия дописывает третий D в младшую половину `[E08]`. Поэтому нормальное окончание физического потока — DD либо DDD. Воспроизведение останавливается уже на первом D; исходный основной цикл проверяет его до начала следующего раунда `[E17]`.

В поставке обнаружена существенная особенность сохранения. `0E92:0067` открывает файл с флагами `8104h` `[E07]`. Это `O_BINARY | O_CREAT | O_RDWR`; флага `O_TRUNC` (`0200h`) нет. Назначение бита `0200h` видно непосредственно в оригинальном CRT: `0000:2D99` проверяет этот бит и только при его наличии вызывает усечение `[E20]`.

Следствие: если новая запись короче старой, после её DD/DDD остаётся прежний конец файла. Там могут находиться правдоподобные движения и даже прежние блоки E с результатами. **Они не являются продолжением текущего воспроизведения.** Их нельзя включать в число живых раундов или приписывать нынешним участникам по текущему заголовку.

Восстановленный JSON хранит такие неиспользуемые байты в `trailing_bytes_hex`, без присвоения им ложной игровой семантики. При обратной записи хвост сохраняется точно. Поле `_recording_storage_end_file_offset` задаёт первую позицию после штатного DD/DDD. Поле `_playback_stop_nibble_index` задаёт индекс первого D относительно начала упакованного потока, начиная с нуля.

| Файл | Полный размер | Конец текущего хранимого потока | Неиспользуемый старый хвост |
|---|---:|---:|---:|
| `ANTONY.REC` | 1755 | 1163 | 592 байта |
| `HANTER.REC` | 1733 | 1733 | 0 |
| `JOKER.REC` | 1762 | 1172 | 590 байт |
| `REMBO.REC` | 2041 | 1141 | 900 байт |
| `SS.REC` | 1726 | 1726 | 0 |

Все пять текущих записей содержат по одному блоку результата до первого D. Старые хвосты объясняют дополнительные E/DD/DDD, видимые при наивном сканировании до физического EOF.

## 6. Использование восстановленных инструментов

Из каталога пакета:

```bash
python3 tools/snk_rec.py decode original/TEST.SNK TEST.json
python3 tools/snk_rec.py encode TEST.json TEST.SNK

python3 tools/snk_rec.py decode original/REMBO.REC REMBO.json
python3 tools/snk_rec.py encode REMBO.json REMBO.REC

python3 tools/snk_rec.py verify original --report snk-rec-check.json
python3 tools/verify_snkrec_c.py original --report snk-rec-c-check.json
```

Пути к исходной поставке нужно заменить, если она хранится в другом каталоге. Нормальная работа Python-инструмента не требует внешних зависимостей. Опция `--exe original/SNAKE.EXE` у `verify` дополнительно запускает машинный эталон и требует Python-пакет Unicorn.

`encode` собирает файл из полей, строк, матриц и событий. У SNK количество карт рассчитывается по списку `cards`, накопительный XOR и контрольный байт вычисляются заново. Сохранённый `_source_sha256` — метаданные для аудита, а не источник двоичного содержимого. REC восстанавливается из таблицы участников, токенов решений, результатов и сохранённого неиспользуемого хвоста.

### C89/Borland

Структуры в `src/snkrec.h` имеют упаковку 1 байт. Проверки размеров выполняются на стадии компиляции обычными C89 typedef-массивами: паспорт 105, клетка 3, карта 152, максимальная структура змеи 1473 байта. Для Borland применяется `far`; на современном хосте макрос разворачивается в пустую строку. Все файлы необходимо открывать в двоичном режиме.

Проверенная команда для исходного 16-битного окружения Borland 3.1:

```text
bcc -ml -a- -k -O -r- -Z -G- -c snkrec.c
```

Здесь `-ml` выбирает large model, `-a-` — побайтовую упаковку, `-k` — стандартный стековый кадр, `-r-` отключает автоматическое размещение переменных в регистрах, `-Z` убирает повторные загрузки адреса, `-O` включает нужную локальную оптимизацию. При `-O-` компилятор оставляет лишний `JMP +0` перед эпилогом функций с возвращаемым значением; с `-O` код совпадает с оригиналом. Полная команда сборки проверочного EXE с путями INCLUDE/LIB сохранена в `analysis/snk_rec_borland/BUILD.BAT`.

Получено следующее прямое совпадение:

| C-функция | Исходный CS:IP | Размер | Результат |
|---|---|---:|---|
| `snk_encode` | `0B2B:000F` | 55 | 55 из 55 байтов |
| `snk_decode` | `0B2B:0046` | 61 | 61 из 61 байта |
| `snk_complement_password` | `044D:022F` | 30 | 30 из 30 байтов |

У этих процедур нет перемещаемых операндов или внешних вызовов, поэтому нормализация адресов не нужна. `tools/snk_rec_borland_check.py` находит функции по MAP проверочного EXE и сравнивает их с установленными диапазонами исходного EXE. Это совпадение трёх процедур; остальной C89 API форматов имеет восстановленную семантику и новое оформление. Проверочный `V6.EXE` — небольшая программа чтения/записи форматов, не пересобранная игра.

Проверка современным `cc` отдельно выполнена со строгими параметрами `-std=c89 -pedantic -Wall -Wextra -Werror`; все 20 файлов восстановлены точно. Современная сборка проверяет корректность C89-кода и форматов, а указанное выше сравнение с результатом Borland подтверждает тождество генерации инструкций для трёх процедур.

API `snk_read`/`snk_write` работает с типизированной структурой. REC API разделяет чтение заголовка, переключение в полубайтовый режим, чтение токена и чтение двухбайтовых результатов. `rec_finish_write` дополняет неполный байт токеном D. Создание/усечение файла оставлено вызывающему коду: архивный драйвер создаёт новый файл и воспроизводит старый хвост явно, поэтому не зависит от исторической ошибки отсутствующего `O_TRUNC`.

## 7. Границы установленного

Восстановлены точное байтовое кодирование, ширины и смещения всех полей SNK, размещение и смысл карт, паспортный заголовок REC, упаковка токенов, длина и порядок результатов, окончание записи и причина старых хвостов. Эти выводы подтверждаются машинным кодом и точным пересозданием всех предоставленных образцов.

Не установлены исходные авторские названия C-типов/полей, точное UI-назначение кода элемента 2 и все визуальные названия пяти цветовых логических групп. Форматный инструмент не выдаёт отдельным токенам решений роль «номер змеи» или «направление» без симуляции поля. Проверка файлов не доказывает полную совместимость DOS-интерфейса, звука, графики, таймингов или всей игры.

Для нестандартных версий, некорректных длин, повторяющихся слотов и повреждённых контрольных байтов правила проверки восстановленных инструментов строже некоторых ветвей исходной программы. Изученные исходные файлы принимаются и пересоздаются без изменения единого байта.
