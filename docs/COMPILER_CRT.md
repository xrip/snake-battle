# Компилятор, модель памяти и библиотека времени выполнения

## Вывод, который действительно подтверждён

Исполняемый файл использует **Borland-совместимую модель Large** и стартовый модуль,
побайтово совместимый с `C0L.OBJ` из исследованной поставки **Borland C++ 3.1**.
Совместимость подтверждена на всём кодовом сегменте стартового модуля и на большой
части CRT, а не только по строке copyright. Исследованный `C0L.OBJ` из Borland C++ 2.0
не совпал. Многие короткие библиотечные функции одинаковы в обеих поставках, поэтому
их совпадение само по себе не определяет версию.

**Единственную историческую версию компилятора установить этим сравнением нельзя.**
Не сравнивались все поставки Borland/Turbo C++ 3.x, а пользователь мог заменить
библиотеку или стартовый модуль. Найденная BC3.1 — конкретная подтверждённая основа
для повторной сборки, не доказательство идентичности исходной среды автора во всех
деталях. Исходный текст C нельзя восстановить однозначно из совпадения машинного кода.

Метка `__MMODEL` из PUBDEF находится по **image `0x0293` / file `0x1293`**. В оригинале
там `04 C0`, то есть `0xC004`. В `LIB/STARTUP/RULES.ASI` исследованной поставки Large
определён как `0x8000 + 0x4000 + 4`: дальние указатели кода и данных. Соответствующий
ключ BCC — `-ml`. Этот вывод проверяет значение маркера, а не предполагает модель по
имени C0L.

Сохранённый [лог сборки GPFTEST](../build/dos/GPFTEST.LOG) сообщает BCC 3.1 и Turbo
Link 5.1. Прилагаемые здесь скрипты анализируют исходные `.OBJ`/`.LIB`; они не заменяют
их скачанной таблицей сигнатур.

## Адреса и метод сравнения

Все `file`-адреса — смещения внутри оригинального `SNAKE.EXE`; все `image`-адреса —
смещения после загрузки MZ-образа без PSP и без добавления выбранного DOS сегмента.
В этом файле MZ-заголовок имеет длину `0x1000`, поэтому `file = image + 0x1000` для
байтов, действительно представленных в файле. Данные BSS за концом образа имеют
`file_offset: null` в JSON.

`tools/omf.py` разбирает THEADR, LNAMES, SEGDEF, GRPDEF, PUBDEF/LPUBDEF, EXTDEF,
COMDEF, LEDATA, LIDATA и FIXUPP. Учитываются переменные индексы OMF и frame/target
threads. Неподдерживаемая релокация внутри развёрнутого LIDATA вызывает явную ошибку,
а не молчаливое сопоставление неверной маски. Во всех исследованных CRT CODE-сегментах
таких релокаций не встретилось. Неизвестные записи остаются в инвентаре записей.

Сопоставление выполняется следующим образом:

1. Из LEDATA/LIDATA собирается сегмент с отдельной картой реально заданных байтов.
2. Только поля, описанные FIXUPP, исключаются из прямого сравнения. Это необходимые
   изменения адресов при линковке, а не произвольная маска несовпавших байтов.
3. Для `CALL FAR` с соответствующей pointer-релокацией дополнительно допускаются
   две конкретные пятибайтовые замены TLINK: `90 0E E8 xx xx` и `0E E8 xx xx 90`.
   Для `JMP FAR` с pointer-релокацией аналогично допускаются `90 90 E9 xx xx`
   и `E9 xx xx 90 90`. Иные последовательности не принимаются.
4. Ищется полное совпадение остальных байтов сегмента; фиксируется уникальность.
5. Если адрес вызываемого символа независимо известен из другого совпавшего PUBDEF,
   проверяется фактическая цель вызова. Для оставшихся far-операндов проверяется
   соответствующая запись в таблице релокаций MZ.
6. Совпавшие алиасы сохраняются как альтернативы. Короткая общая обёртка не получает
   безусловно имя исторического библиотечного модуля.

Подробные поля масок, смещения OMF-записей, все FIXUPP, цели вызовов и MZ-проверки
находятся в `analysis/crt_symbols.json`. В `analysis/crt_bc31_*.json` и
`analysis/crt_bc2_*.json` сохранены результаты только стабильного
сопоставления; для итоговой атрибуции нужно использовать именно `crt_symbols.json`.

## Сравнение поставок


| Проверка | BC3.1 | BC2.0 |
|---|---:|---:|
| Модулей в CL.LIB | 589 | 522 |
| Совпавший полный C0L CODE-сегмент | 661 байт | нет |
| Предварительных CODE-совпадений, включая C0L | 100 | 53 |
| Принятых после проверок целей и MZ | 99 | 53 |
| Различных диапазонов после объединения алиасов | 84 | 40 |
| Покрытых байтов без двойного учёта алиасов | 16111 | 3015 |
| Из них прямо сравниваемых неизменяемых байтов | 14685 | 2861 |
| Независимых проверок целей вызовов/переходов | 181 | 12 |

Покрытие включает совпадающие участки, но не утверждает, что каждый из них был
подключён именно из библиотеки. Особенно это относится к обёртке длиной 18 байт
по `file 0xC393`: DEL и GFREEMEM неразличимы по коду и цели `_free`. Она также могла
быть получена из пользовательского C. Кандидат FFMALLOC имел ту же маскированную
последовательность, но отвергнут: реальный вызов ведёт к `_free` (`image 0x17C9`),
тогда как этот объект требует `_farmalloc` (`image 0x18DD`).

Для C0L: все **536 неизменяемых байтов** совпали в единственном положении `image 0`.
Оставшиеся 125 позиций относятся к FIXUPP или к двум разрешённым заменам far-вызова
на near-вызов. Это не означает 125 фактических различий: часть релокируемых байтов
сохраняет то же значение после линковки. В `crt_symbols.json` задана точная маска.

Отдельно имена, выведенные из операндов FIXUPP, помечены
`inferred_from_OMF_link_references`. У BC3.1 получено **211 меток без противоречий**.
Это полезно для анализа CRT-данных и связей, однако такой вывод не считается
дополнительным независимым доказательством совпадения адреса, из которого он сам
был получен.

## Повторение проверки

Из корня этого пакета. `BC31_ROOT` и `BC20_ROOT` — переменные окружения с путями
к вашим установленным поставкам Borland C++ 3.1 и 2.0. Сам компилятор и его
библиотеки не являются частью пакета; контрольные суммы проверенных файлов
приведены выше. Существующий итог проверки доступен в
[crt_symbols.json](../analysis/crt_symbols.json).

```sh
python tools/crt_match.py \
  --exe original/SNAKE.EXE \
  --candidate Borland_Cpp_3.1 \
    "$BC31_ROOT/LIB/C0L.OBJ" \
    "$BC31_ROOT/LIB/CL.LIB" \
  --candidate Borland_Cpp_2.0 \
    "$BC20_ROOT/LIB/C0L.OBJ" \
    "$BC20_ROOT/LIB/CL.LIB" \
  -o build/crt-recheck.json
```

Для нового объектного файла, в том числе собранного восстановленного C:

```sh
python tools/omf.py dump module.obj -o module-omf.json
python tools/omf.py match module.obj --exe original/SNAKE.EXE -o module-matches.json
```

Вторая команда сопоставляет целый CODE-сегмент. Если в одном объекте несколько
функций и требуется сравнить одну, Python API предоставляет `Module.publics`,
`Segment.data`, `Segment.initialized` и `Segment.fixups`; границы можно взять по
PUBDEF и следующему символу. Имя функции само по себе не является длиной функции.
