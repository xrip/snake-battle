Раздел 1 · Результат и сборка

Snake Battle: восстановление C-кода и форматов

Исследована поставка из snake-battle.zip, содержащая 26 файлов. На извлечённом титульном экране указана версия V 2.3. Работа выполнена по навыку reverse-engineer-anything из morluto/rea, с реальным анализом REA/Ghidra, исполнением отдельных исходных процедур и сборкой восстановленного C оригинальным Borland C++ 3.1 / Turbo Link 5.1.

Состояние результата: восстановлены работающие C-модули игровых правил, движения и файловых форматов. Для семи полных функций подтверждена генерация исходных инструкций Borland. Все 15 SNK, пять REC и весь GPF пересозданы с полным совпадением байтов. Полного C-проекта, собирающего весь исходный SNAKE.EXE байт-в-байт, в этом пакете пока нет.

Имена функций, типов и комментарии назначены при восстановлении. Даже совпадение машинных инструкций не устанавливает исходный авторский текст: разные конструкции C могут давать одинаковые байты. Здесь практический критерий — проверяемый результат компиляции и поведение на исходных данных.

1. Что подтверждено компилятором

Общие параметры, с которыми выполнена итоговая DOS-сборка:

-ml -a- -k -O -r- -Z -G- -M

Модель Large независимо подтверждена маркером __MMODEL = 0xC004 в исходном EXE. Исследованный CRT Borland 3.1 совместим с игрой; стартовый модуль Borland 2.0 не совпадает. Это подтверждает выбранную основу сборки, но не доказывает единственный исторический выпуск компилятора автора среди всех Borland/Turbo 3.x.

  • Полная проверка DOS-сборки.
  • Компилятор и CRT: OMF, FIXUPP, MZ-релокации и библиотечные символы.

Наиболее существенные особенности форматов

SNK: размер файла 107 + 152*N, где N — число карт. Первый байт задаёт начальное состояние накопительного XOR; далее кодируются паспорт и карты. Последний байт дублирует последний кодированный байт. Это не CRC. Клетки карты идут в порядке x, затем y, по три байта {group, negate, symbol}.

REC: заголовок использует XOR, затем кодирование переключается на обычные полубайты, старший первым. Маркер E вводит результаты раунда; D завершает воспроизведение. Токены 0..3 получают смысл из состояния игры, поэтому их нельзя безусловно разбить на пары «змея, направление».

Исходный писатель REC открывает файл без O_TRUNC. Поэтому у ANTONY.REC, JOKER.REC и REMBO.REC обнаружены соответственно 592, 590 и 900 байт старого хвоста после окончания текущей записи. Эти байты сохраняются для точного воспроизведения файла, но не интерпретируются как продолжение боя.

GPF: заголовок 33 байта, далее 82 записи по 22 байта. В архиве 78 обычных LZSS-потоков и четыре полноэкранных ресурса, каждый из четырёх потоков. Получается 94 потока, каждый из которых повторно сжат в исходные байты. У полноэкранного ресурса несжатый размер в каталоге равен нулю; фактический размер — 4 × 28000 = 112000 байт.

BLO: обычные изображения и полноэкранные ресурсы используют противоположный порядок цветовых плоскостей: 3,2,1,0 и 0,1,2,3. Для обычного BLO порядок проверен исполнением исходного GetPixel. Все 58 графических ресурсов представлены в PNG.

SNAKE.ADD, SNAKE_R.TXT, ARTIKLE.TXT: обычные текстовые материалы поставки в DOS-кодировке CP866 с CRLF; расширение ADD в этой поставке не обозначает исполняемый модуль. Они сохранены в исходных байтах.

4. Как повторить сборку оригинальным компилятором

Нужны Python 3.10+, DOSBox и установка Borland с подкаталогами BIN, INCLUDE, LIB. Компилятор не включён в архив. Его происхождение, конкретная версия файлов и SHA-256 приведены в PROVENANCE.md и build/dos/verification.json.

Из корня распакованного пакета:

python3 tools/build_dos.py --compiler /path/to/BORLANDC --dosbox dosbox

Скрипт создаёт отдельный каталог сборки, компилирует четыре программы, запускает их в DOS и сравнивает выходные файлы с исходными. В build/dos/ сохраняются журналы, MAP, OBJ, EXE и verification.json. Существующая исходная поставка в original/ не изменяется. Проверки используют несжатые ресурсы из assets/resources/ и машинные векторы из tests/LOGIC.VEC.

Получаемые программы:

GPFTEST.EXE     проверка 82 записей и 94 сжатых потоков
GPFBUILD.EXE    сборка SNAKE.GPF из ресурсов
SNKRTEST.EXE    чтение и обратная запись SNK/REC
LOGICTST.EXE    1064 проверки игровой логики

Проверка машинного кода после сборки:

python3 tools/snk_rec_borland_check.py \
  --original original/SNAKE.EXE \
  --rebuilt build/dos/SNKRTEST.EXE --map build/dos/SNKRTEST.MAP

python3 tools/verify_bc_codegen.py \
  original/SNAKE.EXE build/dos/LOGICTST.EXE build/dos/LOGICTST.MAP

matching/ содержит также небольшую отдельную сборку четырёх функций логики. Она удобна для исследования генератора кода; основная проверка выше относится к общим C-модулям.

Система адресов доказательств

В исследованном EXE заголовок MZ занимает 0x1000 байт. Адреса CS:IP ниже заданы относительно загрузочного образа, до прибавления сегмента загрузки DOS:

image_offset = CS * 16 + IP
file_offset  = 0x1000 + image_offset

Обозначения [E01]–[E21] ссылаются на подписанные участки в analysis/snk_rec_evidence.txt. Для данных базовый сегмент DGROUP равен 1679h; например, DS:04B7 находится в файле по адресу 0x17C47.

2. Общий алгоритм накопительного XOR

SNK целиком, кроме первого и последнего байта, кодируется накопительным XOR. В REC этим способом кодируется только начальная таблица участников.

Пусть S — открытый начальный байт, P[i] — открытый текст, C[i] — хранимый кодированный байт. Тогда:

C[-1] = S
C[i]  = P[i] XOR C[i-1]
P[i]  = C[i] XOR C[i-1]

При декодировании предыдущий кодированный байт необходимо сохранить до изменения текущего. XOR с постоянным ключом или с предыдущим открытым байтом даст другой результат.

Восстановленный эквивалент двух исходных процедур:

unsigned char far snk_encode(unsigned char far *p,
                             int length, unsigned char seed)
{
    int i;
    unsigned char previous;
    previous = seed;
    for (i = 0; i < length; i++) {
        *p ^= previous;
        previous = *p;
        p++;
    }
    return previous;
}

unsigned char far snk_decode(unsigned char far *p,
                             int length, unsigned char seed)
{
    int i;
    unsigned char previous;
    unsigned char temporary;
    previous = seed;
    for (i = 0; i < length; i++) {
        temporary = previous;
        previous = *p;
        *p ^= temporary;
        p++;
    }
    return previous;
}

Первая процедура расположена в 0B2B:000F, физический адрес 0xC2BF, длина 55 байт [E01]; вторая — в 0B2B:0046, физический адрес 0xC2F6, длина 61 байт [E02]. В исходнике EXE длина — знаковый 16-битный int, указатель — дальний, возврат байта происходит через AL. При нулевой длине обе процедуры возвращают seed. Увеличивается только 16-битное смещение дальнего указателя; нормальные блоки SNK длиной до 1473 байт не требуют перехода через границу сегмента.

Штатное сохранение выбирает seed = random(128): нормальный диапазон создаваемого игрой ключа 00h–7Fh. Сам алгоритм определён для всех 256 значений; проверка исходных процедур включает весь байтовый диапазон случайных входов. Формат не содержит криптографической защиты.

3. Файл .SNK

3.1. Внешняя структура

Смещение в файле Размер Содержание
0 1 Начальный байт XOR seed
1 105 Кодированный паспорт змеи
106 152 × N Кодированные карты, без перезапуска состояния XOR
106 + 152 × N 1 Повтор последнего кодированного байта

N хранится в расшифрованном паспорте. Нормальный диапазон 1..9. Полный размер:

SNK_size = 107 + 152 * N

Возможные размеры штатных файлов: 259, 411, 563, 715, 867, 1019, 1171, 1323 и 1475 байт. Отдельной ASCII-сигнатуры нет. Расшифрованное поле версии равно единице.

Последний байт иногда удобно назвать контрольным, но проверка игры сравнивает его только с последним кодированным байтом. Это не CRC всего файла. Повреждение более раннего кодированного байта способно изменить два соседних расшифрованных байта и пройти эту проверку. Код сравнения находится в 0B33:0BE4 и следующем блоке [E04].

Исходный загрузчик 0B33:0A4C сначала читает и декодирует 105 байт, проверяет версию, вычисляет размер, возвращается в начало файла и читает полный блок [E04]. Формула размера в машинном коде:

0x5C1 - (9 - N) * 0x98 = 105 + N * 152

Для недопустимого количества карт исходный загрузчик временно подставляет N=1 при расчёте размера. Восстановленные библиотечные API отвергают такое значение: сохранение штатных входов остаётся точным, а обработка повреждённых файлов сделана явной.

Исходный сохранитель 0B33:0C6B записывает seed, кодирует блок прямо в памяти, записывает его, затем декодирует тот же блок обратно и записывает последний кодированный байт [E05]. C-реализация сохраняет это свойство: snk_write возвращает переданную структуру в открытый вид даже после ошибки записи кодированного блока.

3.2. Паспорт: 105 байт

Смещения этой таблицы отсчитываются от первого расшифрованного байта паспорта, без seed. В SNK соответствующее физическое смещение на единицу больше. Все 16-битные поля хранятся в little-endian. В строках используется однобайтовая DOS-кодировка; для содержимого поставки подходит CP866.

Смещение Hex Размер Восстановленное поле Значение
0 00 2 version Версия структуры, 1
2 02 2 editor_level 0 новичок, 1 любитель/advanced, 2 эксперт
4 04 2 card_count Количество карт 1..9
6 06 2 battle_count Число завершённых боёв/раундов
8 08 2 rating Рейтинг, исходное значение 1000

Поля интерпретируются восстановленными инструментами как беззнаковые 16-битные значения для сохранения всех комбинаций битов. Оригинальный 16-битный C-код для сравнений и арифметики часто использует знаковый int. Для нормальных значений поставки это различие не меняет результатов. Координаты карт, напротив, явно представлены знаковыми 16-битными числами.

Индекс color не следует ограничивать числом 15: в поставке встречаются 16 и 19. Это индекс варианта окраски/спрайта, а не непосредственный номер одного пикселя EGA. RGB-значения палитры в самом SNK отсутствуют.

Пустое имя не означает отсутствие участника. В REC существуют полноценные записи участников с пустым полем имени.

3.3. Пароль и неиспользованные байты строк

Кроме общего XOR, пароль преобразуется отдельной процедурой 044D:022F, физический адрес 0x56FF [E03]. До первого NUL каждый байт заменяется на 255 - byte. Нулевой терминатор и всё после него остаются без изменений. Повтор того же преобразования восстанавливает строку. Остальные строковые поля этого дополнительного преобразования не имеют.

После первого NUL может оставаться старая информация редактора. Такие байты не являются гарантированным нулевым заполнением. Например, некоторые паспорта содержат пустую текущую строку и ненулевой хвост от прежнего значения. Полное обнуление «неиспользованного» хвоста уничтожает побайтовую идентичность.

Поэтому JSON хранит строку так:

{
  "text": "TEST",
  "after_text_hex": "0000000000"
}

after_text_hex включает терминатор и все оставшиеся байты поля. Для пароля поле text уже содержит результат обратного дополнения, а хвост хранит точные исходные байты. При изменении длины text следует удалить after_text_hex, чтобы сборщик создал новое нулевое заполнение. Иначе проверка ширины обнаружит несоответствие. Поля не преобразуются в Unicode внутри двоичного формата; UTF-8 используется только для JSON.

Ещё одно различие между архивным чтением и загрузкой в игру: после успешного чтения исходная программа заменяет поле name именем загруженного файла без расширения, 0B33:0C48 и далее [E04]. Архивный декодер этого не делает, поскольку такая замена могла бы изменить исходные байты.

3.4. Число боёв и рейтинг

Поле +6 имеет подтверждённый смысл, а не угадано по значениям. В 0729:2C13 значение счётчика раундов текущей сессии DS:340D прибавляется к header+6. Дальше обновляется рейтинг по накопленному результату сессии [E18].

Если R — число раундов сессии, S — суммарный результат змеи за сессию, B — прежнее число раундов в паспорте, то наблюдаемая арифметика такова:

B_new = B + R
delta = S - 10 * R
step  = delta / B_new       # знаковое целочисленное деление к нулю
if step == 0 and delta != 0:
    step = +1 if delta > 0 else -1
rating_new = rating_old + step

Эта формула объясняет назначение обоих полей. Здесь не моделируется переполнение исходного 16-битного int на искусственно больших значениях.

3.5. Карта поведения: 152 байта

Первая карта следует сразу после паспорта, по смещению 105 открытого блока, то есть по физическому смещению 106 файла. Между картами нет указателей, длин и выравнивающих байтов.

Смещение в карте Размер Поле
0 1 Группа рамки карты, выбирающая внешний AND/OR
1 2 Знаковая координата головы head_x
3 2 Знаковая координата головы head_y
5 147 Матрица 7×7; три байта на клетку

Для нормальной карты координаты находятся в диапазоне 0..6. Матрица записана по столбцам: внешний индекс x, внутренний y. Адрес тройки:

card_offset(x, y) = 5 + 21*x + 3*y

Тройка клетки имеет следующий вид:

Байт Значение
+0 Номер цветовой логической группы 0..4
+1 Флаг отрицания; штатные значения 0 и 1

Коды элементов:

Код Значение в сопоставлении

1 Стена/препятствие
2 Значение редакторского шаблона; точное назначение UI не установлено
3 Хвост чужой змеи
4 Хвост своей змеи

Код 2 нельзя объявлять пустотой: исходный сопоставитель сравнивает его как обычное буквальное значение; очистка игрового поля записывает код 0. В данной поставке значение 2 обнаружено в начальном редакторском шаблоне. Семантика соответствующего значка требует отдельного исследования интерфейса.

Общая таблица логики групп хранится в DS:04B7 [E21]:

Группа Логика
0 AND
1 OR
2 OR
3 AND
4 AND

Эта же таблица применяется к байту рамки карты. Цветовая группа является номером логического класса; названия видимых цветов не нужны для восстановления файла и здесь не подменяются догадками о палитре.

Исходный сопоставитель 0729:1058 пропускает коды 8 и 9, для остальных клеток вычисляет (observed_tile == rule_tile) XOR negate. В AND-группе неуспешная клетка обнуляет результат всей группы. В OR-группе учитываются совпавшие клетки. Рамка AND требует ненулевого результата каждой участвующей группы; рамка OR допускает совпавшие группы. Итог содержит и флаг совпадения, и число учитываемых совпадений: последнее используется для сравнения альтернатив. Пустая карта, не содержащая проверяемых клеток, совпадает с оценкой ноль. Полный восстановленный алгоритм находится в src/logic.c.

Карта привязывается к реальной голове координатами head_x/head_y, а не всегда геометрическим центром. Игра рассматривает её повороты и отражение:

Отражение по X:
    head_x' = 6 - head_x
    cell'[x][y] = cell[6-x][y]

Поворот по часовой стрелке:
    head_x' = 6 - head_y
    head_y' = head_x
    cell'[6-y][x] = cell[x][y]

Доказательства преобразований: 0729:000D и 0729:00B4; размер копируемой карты 0x98. Собственная/чужая принадлежность устанавливается при построении обзора: игровые коды хвоста, тела и головы равны 4, 6, 8; если владелец иной, код уменьшается на единицу. Подробные дифференциальные проверки этих процедур входят в материалы восстановления игровой логики.

3.6. Конкретный пример: TEST.SNK

TEST.SNK имеет размер 259 байт и одну карту. Seed равен 68h, версия 1, уровень 0, число боёв 0, рейтинг 1000, дата 16.12.94, индекс окраски 6. Первые байты:

Открытый паспорт: 01 00 00 00 01 00 00 00 E8 03 DF 00 00 00 00 00
Кодированный:    69 69 69 69 68 68 68 68 80 83 5C 5C 5C 5C 5C 5C

Например, первый байт 01 XOR 68 = 69; второй 00 XOR 69 = 69. Конечный контрольный байт файла равен 4Ch.

В карте рамка имеет группу 0, голова находится в (3,3). Клетка (3,2) содержит {group:3, negate:0, tile:3}, то есть условие чужого хвоста перед головой. Клетка (3,3) содержит код 8. Остальные 47 клеток имеют код 9. Этот пример проверяет не только длину блока: он демонстрирует оси матрицы, якорь, тройки правил и смысл кода 3.

4. Файл записи .REC

4.1. Переключение двух разных режимов хранения

REC не является зашифрованным снимком поля. В нём сохранены паспорта участников и поток решений, достаточный для исходной игры, чтобы повторить движение. Карты поведения в REC отсутствуют.

Часть Представление
Первый байт Открытый XOR seed
Таблица участников и её терминатор Накопительный XOR из раздела 2
Поток воспроизведения Открытые четырёхбитные значения, старшая половина байта первой
Возможный хвост после окончания Старое содержимое ранее более длинной записи

Ключевая граница доказана исходным вызовом 0E92:00F8: он включает упакованный режим, сбрасывает фазу полубайта и буфер [E08, E12]. После этой границы XOR не применяется. Попытка расшифровать REC целиком даёт ложную структуру потока.

4.2. Таблица участников

После seed в одном непрерывном XOR-потоке записываются:

slot:u8 + snake_header:105 bytes
slot:u8 + snake_header:105 bytes
...
0x0C:u8

slot — номер участника 0..3, а snake_header имеет точную структуру 105-байтового паспорта SNK. Нет списка карт после него, даже если поле card_count паспорта ненулевое. Указатель присутствия участника определяется наличием записи slot. Поле имени может быть пустым.

Исходный писатель перечисляет присутствующих участников по возрастающему slot. Восстановленный JSON дополнительно сохраняет порядок записей, чтобы обратная запись не требовала сортировки. Номер участника не может повторяться в нормальной таблице.

Если записано K участников, начало полубайтового потока находится по смещению:

packed_stream_offset = 1 + K*(1+105) + 1 = 2 + 106*K

Во всех пяти поставленных REC K=4, поэтому граница равна 426 байтам, 0x1AA. Читатель таблицы — участок 0729:24F3, писатель — 0729:2577 [E12].

4.3. Порядок полубайтов и значения

Каждый байт ABh представляет сначала токен Ah, затем токен Bh. Между токенами одного события выравнивания по байту нет. Поэтому 0xE может находиться в младшей половине байта, а следующий байт результата начинаться с полубайта следующего физического байта.

Токен Значение
0..3 Номер выбранной змеи либо направление; смысл определяется состоянием игрового алгоритма
0xE Конец раунда; далее результаты присутствующих участников
0xD Конец воспроизведения
4..0xC, 0xF Отдельные штатные события с такими кодами в исследованных потоках не обнаружены

0xC служит терминатором только в байтовом XOR-заголовке. Его нельзя автоматически переносить в набор полубайтовых событий.

Для направления соответствие: 0 вверх, 1 вправо, 2 вниз, 3 влево. Для номера змеи это просто slot из заголовка. Процедура выбора следующего участника 0729:0F27 читает/записывает один токен [E14]; процедура выбора хода 0729:143C читает/записывает направление [E15, E16].

Последовательность нельзя безусловно делить на пары «змея, направление»: когда змее некуда ходить, процедура завершает обработку без записи направления. Чтобы присвоить каждому токену 0..3 роль и номер хода, необходимо воспроизводить состояние поля. Форматный декодер честно сохраняет такие участки как список decisions.tokens, без выдуманных пар. Это не мешает точному восстановлению хранения и разбору результатов.

4.4. Результаты раунда

После токена 0xE идут по два байта на каждого присутствующего участника, в порядке slot 0,1,2,3 с пропуском отсутствующих. Эти байты также передаются через полубайтовый канал. Для одного результата получается четыре токена:

score = low_byte + 256*high_byte
tokens = low_byte >> 4, low_byte & 15, high_byte >> 4, high_byte & 15

Пример: результат 31 имеет байты 1F 00 и токены 1,F,0,0. Здесь F — часть результата, а не неизвестное событие. Поэтому сканирование всех полубайтов с поиском маркеров без учёта длины результата неправильно.

Писатель результатов расположен в 0729:04CC, читатель — в 0729:046E [E13]. Оба обходят четыре возможных слота и читают/пишут ровно два байта для присутствующего участника. Для четырёх участников один блок результата занимает 1+16=17 токенов, включая маркер E.

Результаты в поставке неотрицательны и суммируются в 40. В файле хранится обычное 16-битное слово, без отдельного кода знака, десятичного представления или общего результата раунда.

4.5. Конец записи, заполнение и остатки предыдущего файла

В конце исходная игра явно записывает два токена D, затем закрывает файл [E19]. Если второй D оказался в старшей половине байта, процедура закрытия дописывает третий D в младшую половину [E08]. Поэтому нормальное окончание физического потока — DD либо DDD. Воспроизведение останавливается уже на первом D; исходный основной цикл проверяет его до начала следующего раунда [E17].

В поставке обнаружена существенная особенность сохранения. 0E92:0067 открывает файл с флагами 8104h [E07]. Это O_BINARY | O_CREAT | O_RDWR; флага O_TRUNC (0200h) нет. Назначение бита 0200h видно непосредственно в оригинальном CRT: 0000:2D99 проверяет этот бит и только при его наличии вызывает усечение [E20].

Следствие: если новая запись короче старой, после её DD/DDD остаётся прежний конец файла. Там могут находиться правдоподобные движения и даже прежние блоки E с результатами. Они не являются продолжением текущего воспроизведения. Их нельзя включать в число живых раундов или приписывать нынешним участникам по текущему заголовку.

Восстановленный JSON хранит такие неиспользуемые байты в trailing_bytes_hex, без присвоения им ложной игровой семантики. При обратной записи хвост сохраняется точно. Поле _recording_storage_end_file_offset задаёт первую позицию после штатного DD/DDD. Поле _playback_stop_nibble_index задаёт индекс первого D относительно начала упакованного потока, начиная с нуля.

Все многобайтные числовые поля GPF — little endian. Каталог расположен сразу за заголовком. Его порядок значим для побайтового восстановления и сохранён.

2.1. Заголовок: 33 байта

Смещение Размер Тип Значение / смысл
0x00 19 bytes 1A + ASCII GAMOS PACKED FILE + 00
0x13 4 bytes 01 00 00 01; отдельная семантика этих четырёх байтов не установлена

Значения 01 00 00 01 недостаточно, чтобы объявить конкретные поля версией, числом томов или флагами. Из исследованного чтения достоверно следует только размер заголовка и расположение счётчика записей.

Доказательство: функция file 0x12DB6 читает 0x21 байт в DS:4104. Поиск file 0x12E1D перемещается на смещение 0x21, читает записи по 0x16 байт и сравнивает счётчик цикла с DS:411B, то есть с header + 0x17.

2.3. Способы хранения

1 — отдельный поток LZSS. В каталоге есть оба размера. Декодер получает упакованную длину; отдельного маркера конца внутри потока нет.

2 — четыре сжатые плоскости полного EGA-экрана. Блок содержит четыре пары: u16 compressed_length и следующие compressed_length байт LZSS. Каждая плоскость распаковывается ровно в 28 000 байт. Полный ресурс — 112 000 байт. Каталожный несжатый размер равен нулю, поскольку формат использует отдельный путь обработки, а 112 000 не помещается в u16.

У исходного загрузчика есть и путь выдачи данных без распаковки, используемый для получения блока способа 2 целиком. Значение способа 0 не встречается среди 82 записей; поддержка raw в утилите является отдельной возможностью реализации, а не утверждением о наблюдавшихся ресурсах игры.

3. Алгоритм сжатия LZSS

3.1. Состояние

  • кольцевой словарь: 4096 байт;
  • начальная позиция записи: 0xFEE = 4078;
  • позиции 0..4077 перед каждым вызовом заполняются ASCII-пробелом 0x20;
  • последние 18 байт оригинальный декодер не очищает;
  • длина совпадения: 3–18 байт;
  • источник совпадения — абсолютный индекс в кольцевом словаре, не расстояние назад.

Ни один из 94 потоков не обращается к последним 18 неинициализированным байтам раньше их записи в текущем вызове. Python-декодер дополнительно проверяет это. Поэтому результат в данном наборе ресурсов не зависит от предыдущего вызова.

3.2. Флаги и токены

Перед группой до восьми токенов находится байт флагов. Биты используются от младшего к старшему:

Бит Содержимое токена
1 Один буквальный байт
0 Двухбайтовое описание совпадения

Для совпадения сначала читается младший, затем старший байт слова token:

source_index = token & 0x0FFF;
length       = (token >> 12) + 3;

Копирование выполняется последовательно через кольцевой словарь. Для каждого байта источник читается до записи в текущую позицию словаря. Поэтому самоперекрывающиеся совпадения корректны и позволяют, например, развернуть длинную цепочку нулей. После каждого байта обе позиции маскируются & 4095.

Последняя группа может содержать меньше восьми токенов: окончание определяется исчерпанием входной длины. Неиспользованные биты последнего флага не означают дополнительных данных.

3.4. Почему обычного LZSS-упаковщика недостаточно для точного совпадения

Один и тот же несжатый массив можно представить множеством корректных потоков. Для этого файла восстановлен также детерминированный выбор совпадения: упорядоченные бинарные деревья по первому байту, окно 4096, максимальная длина 18, вставка начальных узлов в порядке r-1…r-18, выбор только строго более длинного совпадения и замена узла при полном совпадении длины 18.

Эти детали определяют, на какую из нескольких равных последовательностей сошлётся упаковщик. Здесь такой алгоритм даёт точное совпадение всех потоков. В проекте не хранится «карта исходных токенов» для подстановки результата.

5. Обычные .BLO: дескриптор и плоскости

5.1. Расположение

У всех 54 обычных .BLO есть 16-байтовый дескриптор изображения, затем 16 сохраняемых байтов, затем четыре плоскости. Начало каждой плоскости выровнено на 16 байт. Размер строки выровнен на слово, а не только на байт.

Смещение Размер Смысл
0x00 2 Ширина в пикселях
0x02 2 Высота в пикселях
0x04 2 Шаг строки в байтах
0x06 1 Упакованные свойства дескриптора; в файлах 0x18
0x07 1 Дополнительное байтовое смещение начала растровых данных; здесь 0
0x08 8 Четыре u16-смещения плоскостей в параграфах по 16 байт
0x10 16 Сохранённый хвост заголовочной области; устойчивое файловое назначение не установлено
далее переменно Четыре плоскости с выравниванием

Для встречающихся файлов:

stride          = 2 * ceil(width / 16)
plane_bytes     = stride * height
plane_allocated = 16 * ceil(plane_bytes / 16)
file_size       = 32 + 4 * plane_allocated
plane_offset[p] = 32 + p * plane_allocated

Часть хвостовых байтов выглядит как состояние/остаточные данные создавшего файл инструмента; у LETTER.BLO есть отличающиеся ненулевые значения. Их происхождение не доказано. Удалять их или обнулять при побайтовой реконструкции нельзя. Для чтения пикселей из данных этого архива они не нужны.

5.2. Свойства дескриптора

Создание дескриптора восстановлено в расшифрованном драйвере, file-equivalent 0x128C6..0x12958, относительная функция драйвера 0x2B60.

  • flags & 7: горизонтальное смещение первого пикселя внутри байта;
  • (flags >> 3) & 3: число цветовых плоскостей минус один;
  • бит 0x40: дополнительная плоскость/режим маски;
  • бит 0x80: выбор пути для аппаратной EGA-памяти;
  • бит 0x20 в обнаруженном конструкторе не устанавливается.

В исследуемых файловых ресурсах всегда flags = 0x18: четыре обычные плоскости, нулевое битовое смещение, без дополнительной маски. Поддержка произвольных иных режимов драйвера требует отдельной проверки; документация не объявляет их полностью исследованными только по конструктору.

При работе в памяти слова plane_offset преобразуются в реальные сегментные адреса. В файле сохранены относительные параграфы. Нельзя интерпретировать исходное значение 2 как смещение на два байта.

5.3. Важное отличие: порядок плоскостей противоположен полноэкранному

У обычного .BLO первая плоскость даёт бит 3 цвета, последняя — бит 0.

pixel = 0
for plane in range(4):
    byte = data[plane_offset[plane] + y * stride + x // 8]
    pixel = (pixel << 1) | ((byte >> (7 - x % 8)) & 1)
Порядок плоскости Вес цвета для обычного .BLO Вес для полноэкранного способа 2
0 8 1
1 4 2
2 2 4
3 1 8

Это установлено по функции чтения пикселя оригинального расшифрованного драйвера file-equivalent 0x127DA, относительное смещение 0x2A74, и проверено её выполнением в Unicorn. Например, у BODYALL.BLO пиксель (1,0) имеет биты плоскостей [1,0,0,0]; оригинальная функция возвращает 8, а не 1. Код gpf_blo_pixel в C повторяет этот порядок.

PNG используют стандартную 16-цветную EGA-палитру и сохраняют исходные пиксели. Это извлечение изображений; реальный видеорежим и динамическая смена палитры полной игры не запускались в рамках этой проверки ресурса.

6. .SND: банки инструментов AdLib

Эти файлы содержат определения инструментов FM-синтезатора, а не PCM-звук. Структура соответствует раннему банку тембров AdLib; названия параметров сопоставлены с независимой реализацией AdPlug mus.cpp и composer.cpp. Размеры, имена и значения прочитаны из ресурсов игры.

6.1. Заголовок и массивы

Смещение Тип Смысл

1 u8 Младшая версия: 0

Смещение Тип Смысл

7.2. События

Каждое событие начинается с задержки. Байт F8 добавляет 240 тиков; после цепочки таких байтов читается завершающая однобайтовая часть задержки. Это не MIDI VLQ. Затем следует команда либо данные с ранее установленным running status.

Старший полубайт / команда Данных Смысл
8n 2 Выключение ноты
9n 2 Нота и громкость; нулевая громкость выключает ноту
An 1 Изменение громкости; здесь один байт, в отличие от MIDI polyphonic key pressure
Bn 2 Контроллер и значение
Cn 1 Номер инструмента
Dn 1 Channel pressure
En 2 Pitch bend
F0 ... F7 переменно System exclusive; в ресурсах есть управление темпом
FC 0 Конец композиции

Для темпа встречается последовательность F0 7F 00 integer fraction F7, которая задаёт множитель основного темпа integer + fraction/128.

Парсер в tools/gpf_meta.py проходит все события до конца и сохраняет адреса, накопленные тики и явность running status. Он не синтезирует звук.

8. .MID: стандартные MIDI-файлы

Три файла имеют обычную структуру SMF:

  • MThd, big-endian длина 6;
  • format 0, один трек, division 480;
  • MTrk, big-endian длина данных;
  • события с MIDI VLQ-задержками, channel status/running status, meta и SysEx.

MUS1.MID: 44 146 байт; MUS2.MID: 36 433; MUS3.MID: 15 857. В отличие от внешнего GPF, числовые поля заголовков SMF имеют big-endian порядок. Все три трека структурно разобраны до объявленного конца. События доступны в analysis/gpf-metadata/*.MID.json; исходные MIDI можно открыть отдельно от игры.

Наличие .MID внутри контейнера само по себе не доказывает, что конкретная конфигурация звукового драйвера игры их воспроизводит. Структура ресурса и достижимость кода выбора устройства документируются отдельно.

9. Тексты и локализация

ENGLISH.TXT, RUSSIAN.TXT, SWEDEN.TXT — байтовые DOS-тексты с CRLF. Для русского текста требуется CP866, а не Windows-1251 и не UTF-8. Первые шесть строк — клавиатурные/символьные таблицы; далее идут позиционно адресуемые подписи интерфейса, сообщения и титры. Это не словарь ключ=значение. Порядок строк является частью формата.

Варианты RUSINSTR.TXT и ENGINSTR.TXT содержат пользовательские инструкции. Ресурсы заканчиваются служебными строками/пустыми строками и DOS EOF 0x1A. Эти байты сохраняются. Простое открытие и пересохранение UTF-8-редактором с нормализацией переводов строк изменит ресурс и нарушит точное совпадение.

В analysis/gpf-metadata/ есть UTF-8-копии для чтения и JSON с индексом каждой строки. Они не заменяют байтовые файлы в assets/resources/ при сборке.

10. PASSW.RUS / PASSW.ENG

Это таблицы слов для экранной проверки по координатам, связанные с печатной сеткой. Они отделены от паролей отдельных змей .SNK.

Смещение Размер Поле
0 2 Число записей: 100
2+18*i 1 Буква колонки: ASCII A…E
3+18*i 1 Номер строки: 1…20
4+18*i 16 Накопительно XOR-кодированное слово

Полный размер: 2 + 100*18 = 1802 байта.

Алгоритм декодирования записи:

previous = column_byte ^ row_byte
for encoded in record[2:18]:
    decoded.append(encoded ^ previous)
    previous = encoded

Результат — пятибуквенное слово, повторённое три раза, и нулевой байт. Например, английская клетка A1 содержит JELLYJELLYJELLY\0, русская — СЦЕНАСЦЕНАСЦЕНА\0 в CP866.

Подтверждающий код выбора записи: image 0xC6D1 / 0xC721; формирование повторения и сравнение: image 0xC7A2..0xC7F7 (для file-адресов прибавить 0x1000). Полные таблицы в JSON созданы для изучения содержимого ресурсов. В исполняемом файле проверка не отключалась.

11. Сборка и воспроизведение проверок

C89 / Borland C++ large model

В пакете сохранены результаты реальной DOS-сборки Borland C++ 3.1: лог компилятора, проверка 82 ресурсов и 94 потоков, вывод сборщика GPF и повторно собранный архив. Полные параметры использованной сборки находятся в BUILD.BAT. Ниже приведены отдельные команды для инструментов.

Из каталога src:

bcc -ml -egpftest.exe gpftest.c gpfcodec.c
bcc -ml -egpfbuild.exe gpfbuild.c gpfcodec.c
bcc -ml -DGPF_STANDALONE -egpfcodec.exe gpfcodec.c

Проверка 94 исходных потоков:

gpftest ..\original\SNAKE.GPF

Повторная сборка всего GPF из распакованных ресурсов:

gpfbuild ..\assets\resources ..\build\SNAKE.GPF

Извлечение отдельного ресурса:

gpfcodec ..\original\SNAKE.GPF BODYALL.BLO BODYALL.BLO

Для GCC те же исходники собираются в строгом C89:

gcc -std=c89 -pedantic -Wall -Wextra -Werror src/gpftest.c src/gpfcodec.c -o gpftest
gcc -std=c89 -pedantic -Wall -Wextra -Werror src/gpfbuild.c src/gpfcodec.c -o gpfbuild

Код явно разбирает числа и не зависит от выравнивания C-структур. В DOS используются 16-битные длины блоков и отдельные буферы плоскостей; словарь и дерево совпадений выделяются в heap, чтобы не переполнять обычный DOS stack.

Python 3

Из корня проекта:

python3 tools/gpf.py pack assets/gpf_manifest.json build/SNAKE.GPF
python3 tools/gpf.py verify original/SNAKE.GPF assets/gpf_manifest.json

12. Остаточные неизвестные

  1. Точное назначение четырёх байтов заголовка GPF 0x13..0x16 и резервного хвоста: их значения в единственном исследованном контейнере не позволяют различить возможные назначения.
  2. Происхождение неодинаковых 16 байт заголовочной области обычных .BLO: значения сохранены, но для чтения пикселей не нужны; поведение исходного инструмента, записавшего их, не установлено.
  3. Полная спецификация неиспользуемых в этих ресурсах режимов маски/видеопамяти графического дескриптора: все файловые образцы имеют flags = 0x18, поэтому они не проверяют остальные варианты.
  4. Причина расхождения счётчиков отдельных .MUS с событийным потоком: расхождения измерены, но принятую авторским генератором систему подсчёта эти данные однозначно не определяют.
  5. Синтез звука и соответствие конкретному аппаратному драйверу здесь не проверялись: выполнен структурный разбор событий и инструментов, без проверки итогового звукового сигнала на соответствующем устройстве.

Эти неизвестные не мешают извлечению всех данных, правильному чтению пикселей исследованных изображений и доказанной побайтовой повторной сборке GPF.

Структура MZ-файла SNAKE.EXE

Объект и источники

Документ описывает исходный EXE в пакете, размер 102326 байт, SHA-256:

c4e064a1cf15e438017d4d6443817424f816ce4b749fcc279f2d97dc7bd86821

Числа заголовка непосредственно прочитаны из этого файла. Адресное отображение согласовано с сохранённым результатом REA/Ghidra original_load_image.json. Сведения о стартовом коде, DGROUP и встроенном драйвере опираются на уже разобранные инструкции; новых запусков программы для этого документа не выполнялось. Все интервалы вида [начало, конец) ниже включают начало и исключают конец.

Все слова — 16-битные little-endian; единица «параграф» означает 16 байт. Названия e_* здесь обозначают стандартные поля MZ, а не символы восстановленного авторского исходника.

Это значения при передаче управления стартовому коду. Позднее CRT сам меняет SS:SP; подменять поля MZ итоговым рабочим стеком нельзя. Нулевое e_csum фиксирует содержимое поля, но не является самостоятельным доказательством проверки контрольной суммы.

Размер файла, заголовка и загрузочного образа

Поскольку e_cblp ненулевое, объявленный размер вычисляется так:

file_size   = (e_cp - 1) * 512 + e_cblp
            = 199 * 512 + 438 = 102326 = 0x18FB6
header_size = e_cparhdr * 16 = 256 * 16 = 4096 = 0x1000
image_size  = file_size - header_size = 98230 = 0x17FB6

Объявленный размер совпадает с фактическим. Загрузочный образ занимает файловый диапазон [0x1000,0x18FB6). За его объявленным концом в этой поставке нет добавленного файлового хвоста. Это утверждение о внешней структуре файла; оно не исключает встроенных данных или кодированного кода внутри самого образа.

Байты 0x1C..0x3D, то есть 34 байта между основными полями и таблицей релокаций, сохраняются как дополнительная область заголовка без установленной здесь семантики. Они начинаются с 01 00 FB 50 6A 72, после чего следуют 28 нулей. Оснований объявлять эту область расширенными полями PE нет. В частности, нельзя автоматически считать DWORD по адресу 0x3C указателем на заголовок PE: здесь с 0x3E уже начинается собственная таблица MZ-релокаций.

Таблица релокаций и заполнение

Таблица начинается по файловому адресу 0x3E и содержит 879 записей по 4 байта, всего 3516 байт:

record[i] = offset:u16le, segment:u16le
table_end = 0x3E + 879*4 = 0xDFA

Каждая пара задаёт место исправляемого 16-битного слова, а не окончательный адрес вызываемой функции. Позиция слова относительно загрузочного образа равна segment*16+offset. При загрузке к хранимому там сегментному значению прибавляется L; арифметика слова остаётся 16-битной.

Первая запись указывает на 0000:0001. По файловому адресу 0x1001 находится слово 1679h внутри первой инструкции MOV DX,1679h. При анализе с L=1000h оно становится 2679h. Это конкретный пример того, почему загруженные байты могут отличаться от файловых, хотя исходный EXE не изменён.

Порядок записей не монотонный: среди первых записей за 03EF:002F следует 03EF:002A. Для точной реконструкции необходимо сохранить исходный порядок, даже если иной порядок исправлений дал бы те же значения в памяти.

Диапазон [0xDFA,0x1000) содержит 518 нулевых байт заполнения. Полное разложение заголовка:

28 основных байт + 34 дополнительных + 3516 релокаций + 518 заполнения = 4096

Заполнение не относится к коду игры, однако участвует в сравнении файлов и SHA-256.

Файловые, относительные и REA-адреса

В документации пакета segment:offset обычно относится к образу до добавления DOS-сегмента загрузки. Для байтов, действительно представленных в файле:

I = 16*segment + offset          # смещение в образе
F = 0x1000 + I                  # смещение в EXE
A = 0x10000 + I                 # линейный адрес REA/Ghidra этого анализа
F = A - 0xF000

REA использовал фиксированный сегмент загрузки 1000h, то есть линейную базу 10000h. Это выбранная координатная система статического анализа, а не измеренный адрес процесса DOS. Например, сопоставитель 0729:1058 имеет I=82E8h, F=92E8h, A=182E8h. Линейный адрес сам по себе не задаёт единственную пару segment:offset: у реального режима существуют адресные псевдонимы.

В общем случае физический адрес при загрузке в L равен 16*L+I. Эти формулы нельзя применять к заголовку MZ как к игровому коду или приписывать ими файловые байты неинициализированной памяти.

DGROUP, BSS и рабочая память

MZ-заголовок не содержит отдельного поля DS. Базовый сегмент данных 1679h установлен по стартовым инструкциям и ссылкам CRT. Инициализированная часть DGROUP находится в образе по [0x16790,0x17FB6), в файле по [0x17790,0x18FB6). Это 6182 байта, относительные смещения DS 0000h..1825h.

Дальше следуют данные, для которых в EXE нет исходных байтов. Стартовый код 0000:00AC..00BC явно обнуляет диапазон DS [1826h,6290h): устанавливает нулевой AL, DI=1826h, длину 6290h-1826h и выполняет REP STOSB. Размер этой области — 19050 байт. Это прямое основание отделять BSS от файлового DGROUP. Например, игровое поле в DS:1B55 относится к рабочей памяти; искать его начальное содержимое по искусственно вычисленному файловому адресу неверно.

Дополнительный запрос MZ 1199*16=19184 байта относится к размещению памяти, включая область за файловым образом; это не длина ещё одного блока данных внутри EXE. В сохранённом отображении REA дополнительная область помечена initialized:false, а file_offset равен null. Резервирование, обнуление BSS и начальный стек следует рассматривать раздельно. Подробнее о доказательствах CRT — COMPILER_CRT.md.

Кодированный драйвер и точное воспроизведение EXE

Встроенный графический драйвер имеет заголовок по файловому адресу 0xFD66 и кодированный блок [0xFE16,0x12D36) размером 12064 байта. После декодирования его инициализатор перемещает часть кода на 22 байта вниз. Поэтому для этого участка адрес до декодирования и адрес исполняемой инструкции после инициализации различаются. Алгоритм и отдельные адресные формулы приведены в разделе «Кодированный графический драйвер» ARCHITECTURE.md.

Совпадение отдельных скомпилированных C-функций ещё не даёт тождественного EXE. Для полного результата должны совпасть состав и порядок объектных модулей, выбор CRT-функций, размещение сегментов и данных, адреса вызовов, величина BSS и стека, таблица релокаций с её порядком, все поля и дополнительные байты заголовка, заполнение и исходное кодированное представление драйвера. Функционально одинаковые загрузочные образы могут иметь разные файловые байты. Поэтому проверка полного восстановления должна сравнивать весь файл, а также отдельно объяснять совпадение кода и компоновки, не заменяя эти задачи сохранённой копией исходного EXE.

Поле

Поле хранится в DS:1B55 как board[37][37]. Индекс X внешний: адрес клетки равен base + 148*x + 4*y. Клетка занимает4байта: owner — 16-битный номер участника и kind — 16-битный тип. Планировщик

Четыре флага DS:1B4D отмечают активных участников, четыре флага DS:1B45 — ожидающих хода в текущем проходе. Счётчики находятся в DS:1B41 и DS:1B43. Когда ожидающих не осталось, их набор копируется из активного. Случайное число задаёт начальный слот0…3; затем идёт круговой поиск первого ожидающего. Выбранный флаг сбрасывается. Это не равновероятный выбор из компактного массива активных слотов: вероятность зависит от промежутков между ними. [Доказательство: 0729:0F27; логическое извлечение sb_select_pending_slot.]

DS:340F считает существующие змеи, включая неподвижный остаток длины1; DS:3411 отмечает факт выполненного перемещения. Змея длины1 исключается из активного и ожидающего наборов, но окончательно исчезает только после поедания последнего сегмента. [Доказательство: 0729:0BEC, подтверждено случаями длины2→1 и1→0.]

Восприятие и правила ИИ

Относительные типы клеток

На поле используются абсолютные типы:0пусто,1стена,4хвост,6тело,8голова. Перед сопоставлением правил строится обзор13×13. Если тип не меньше4 и владелец отличается от текущего участника, из типа вычитается1. Поэтому карты могут различать свои и чужие части. [Доказательство: 0729:1493…1527.]

Значение в карте/обзоре Смысл Особенность сопоставления
0 Пустая клетка Обычное сравнение
1 Стена Обычное сравнение
2 Назначение редакторского символа не установлено В сопоставителе обычное числовое значение; нельзя заменять пустотой
3 Чужой хвост Обычное сравнение
4 Собственный хвост Обычное сравнение
5 Чужое тело Обычное сравнение

Значения8 и9 игнорируются независимо от группы и отрицания. Наличие8 в карте само по себе не создаёт проверку головы в этой позиции. Положение совмещения задаётся отдельными координатами якоря. [Доказательство: сравнения с8 и9 в 0729:1058; 700дифференциальных случаев.]

Карта7×7

Одна карта занимает152байта: общий режим группы1байт, координаты якоря X/Y по2байта, затем49троек {group,negate,symbol}. Порядок — X снаружи, Y внутри; клетка находится по 5+21*x+3*y. Голова в обзоре находится в [6][6], а клетка карты [x][y] сопоставляется с:

view[6 - anchor_x + x][6 - anchor_y + y]

Размер13 обеспечивает все положения якоря0…6 при размере карты7. [Доказательство: 0729:1058; операции чтения SNK 0B33:0A4C.]

Код использует пять логических групп. Массив семантики равен {AND, OR, OR, AND, AND} для индексов0…4. Та же таблица определяет общий режим карты. Для обычной клетки результат сравнения равен (наблюдаемый_символ == символ_карты) XOR negate. В корректных картах negate имеет значение0или1. [Доказательство: локальные массивы и ветвления 0729:1058.]

В AND-группе любой провал обнуляет результат группы и оставляет его нулевым до конца проверки. Последующее совпадение не «восстанавливает» такую группу. В OR-группе считается число совпавших условий. Общий AND требует ненулевого результата каждой встреченной группы; общий OR суммирует успешные группы и требует хотя бы один успех. Карта без единой учитываемой клетки признаётся совпавшей со счётом0. [Доказательство: полный перевод sb_match_card; analysis/game_logic_verification.json.]

Результат имеет два16-битных поля {matched,score}. При неуспехе поле score иногда остаётся положительным: финальный цикл успевает прибавить счёт ранней группы, прежде чем встретить неуспешную AND-группу. Поэтому валидность обязательно проверяется отдельно. Сравниватель считает любые два неуспеха равными, успех всегда выше неуспеха, а два успеха сравнивает по счёту. Возвращаемые значения:0хуже,1равно,2лучше. [Доказательство: 0729:1002, 0729:1058; 64проверки сравнивателя.]

Повороты и отражения

0729:000D отражает X: якорь становится (6-x,y), клетка [x][y] берётся из [6-x][y]. 0729:00B4 поворачивает по часовой стрелке: якорь становится (6-y,x), исходная клетка [y][x] записывается в [6-x][y]. Оба преобразования сохраняют все три байта клетки и общий режим. [Доказательство: по150дифференциальных примеров каждого преобразования.]

Перед боем 0729:015B выделяет 0xAB00 =43776байт для кэша 4участника ×4поворота ×2отражения ×9карт ×152байта. Шаг участника — 0x2AC0, поворота — 0xAB0, отражения — 0x558. Сначала создаются обычный и отражённый варианты направления0, затем каждый из них последовательно поворачивается. В C-извлечении варианты вычисляются локально, без полного кэша. [Доказательство: множители и вызовы преобразований в 0729:015B.]

Выбор направления

Функция 0729:143C исключает обратное направление (previous+2)%4, затем проверяет соседей. Типы1,5,6,7 запрещают ход; хвосты3и4 разрешены. После этого карты рассматриваются в порядке их хранения. Для каждого оставшегося направления сравниваются обычный и отражённый варианты; при равенстве выбирается обычный. Сохраняются направления с лучшим результатом. Как только очередная карта даёт хотя бы одно успешное сопоставление, следующие карты не рассматриваются. [Доказательство: 0729:1527…1800.]

Если остаётся несколько направлений, случайное число0…3 задаёт начало кругового поиска первого разрешённого направления. Это тот же тип смещения вероятностей, что у планировщика участников. При отсутствии подходящих карт выбор производится среди законных направлений. При отсутствии законных направлений движение не выполняется. Поэтому в REC нельзя без состояния поля всегда чередовать «слот, направление»: запись направления зависит от возможности хода. [Доказательство: 0729:143C, вызовы записи в 0729:18BC и 0729:0FDE.]

Изменение состояния при ходе

Исходный 0729:0BEC сначала устанавливает флаг движения, увеличивает длину и счёт ходящей змеи, превращает прежнюю голову в тело и создаёт новую голову в предыдущем элементе кольца. Затем анализируется целевая клетка. [Доказательство: прямой дифференциальный запуск180случаев.]

При попадании на хвост тип4 определяется его владелец. У владельца уменьшаются длина и счёт. Если длина стала1, единственный сегмент становится хвостом и участник перестаёт ходить. Если стала0, уменьшается количество существующих змей. Активный/ожидающий флаги и их счётчики корректируются независимо. Если хвост не съеден и параметр обычного хода установлен, убирается собственный старый хвост. В конце новая клетка получает владельца ходящей змеи и тип8. Поедание собственного хвоста следует из той же последовательности операций и не требует отдельной ветки. [Доказательство: 0729:0BEC…0F26; sb_apply_move.]

Начальное выращивание 0729:18EB создаёт первую часть в элементе40, затем вызывает ход без обрезания собственного хвоста, пока длина не достигнет10. Такая последовательность используется в анимации входа 0729:1BB0. Восстановленная sb_seed_snake_step включает изменение состояния, но не рисунки ворот и задержки. [Доказательство: исходные вызовы и сравнение длины с10.]

Профили, счёт и повтор

Рабочие указатели четырёх профилей находятся в DS:34D7. В профиле карты начинаются со смещения 0x69 =105, количество карт хранится в16-битном поле +4. Поле +6 накапливает завершённые раунды. Поле +8 обновляется после боя: учитывается отклонение накопленного счёта от 10 × завершённые_раунды, делённое на обновлённое суммарное количество раундов. Ненулевое отклонение с нулевым целочисленным частным даёт изменение+1или−1. [Доказательство: загрузчик/сохранительSNK; обновления образа 0x9EA3, 0x9EA6, 0x9EF2.]

Модуль REC 0E92 сначала обрабатывает кодированный заголовок с профилями, затем переключается на поток сырых полубайтов. ТокенE сопровождается счётом присутствующих участников; D завершает текущий повтор. В исходной функции открытия записи отсутствует O_TRUNC, поэтому после текущего логического конца могут оставаться байты более старой длинной записи. Их нельзя считать дополнительными раундами текущего повтора. Полные схемы, поля и правила сохранения хвоста изложены в отдельном описании SNK/REC. [Доказательство: 0E92:0067, флаги открытия 0x8104; разбор модулем форматов.]

Кодированный графический драйвер

В EXE присутствует небольшой самостоятельно декодируемый блок драйвера. Его исходный заголовок расположен по файлу 0xFD66. Шесть байтов перед ним принадлежат выравниванию/предыдущей области; начало сегмента 0ED6 в 0xFD60 не совпадает с началом заголовка. В заголовке находятся CALL на обёртку, маркер 0x1234, смещение полезного кода 0x00B0, контрольное значение и длина. [Доказательство: байты заголовка и обёртка файла 0x12D36…0x12DB4.]

Кодированные данные занимают [0xFE16,0x12D36), 12064байта. Декодирование использует8-битное состояние:

state = 0
для каждого cipher:
    state = ROL8(state, 1)
    plain = cipher XOR state
    state = (state + plain) mod 256

Обратное преобразование даёт исходные байты точно. SHA-256 декодированного блока:

329e58a15e80df4c559db734a719a2837346ad3e82a73ca29c8ddeda1d063c90

Обёртка также считает контрольную сумму, но в исследуемом EXE инструкция по файлу 0x12D80 является безусловным переходом, обходящим ветвь отказа. Это наблюдаемое свойство входного файла; восстановительные инструменты не меняли эту инструкцию. [Доказательство: оригинальные байты; analysis/sprite_driver_verification.json.]

После декодирования исходный инициализатор копирует первые 0x2EC0 =11968байт блока вниз на 0x16 =22байта: из адреса образа 0xEE16 в 0xEE00. Последние96байт — сам инициализатор — не копируются. Исходный CALL в заголовке по адресу образа 0xED66 заменяется последовательностью EA B0 00 D5 0E, то есть дальним переходом 0ED5:00B0. [Доказательство: полный запуск обёртки и инициализатора в tools/verify_driver_init.py; analysis/sprite_driver_init_verification.json.]

Для декодированных инструкций справедливо:

условное исходное файловое смещение = 0xFD66 + offset_драйвера
адрес в образе после инициализации = 0xED50 + offset_драйвера

Например, таблица диспетчера CS:0102 происходит из декодированных байтов, соответствующих файловому смещению 0xFE68. Линейный листинг analysis/sprite_driver_linear_listing.txt использует условные файловые смещения; он содержит также области данных, которые дизассемблер может представить как инструкции. Такой листинг не является доказанной картой всех функций драйвера. Файлы sprite_driver_plain.bin и декодирующий скрипт служат материалом анализа; C-модуль игровой логики не встраивает этот машинный код.

Оставшиеся ограничения

Исходные пользовательские имена и точный текст C не извлечены из бинарника; восстановленный C не содержит полной оболочки меню, редактора, всех графических и звуковых функций. Часть sb_choose_direction проверена через Python-модель, но не заявлена как полный дифференциальный запуск исходного 0729:143C со всеми побочными эффектами. В таблице состояния змеи остаётся неименованное поле +4; смысл редакторского символа2 не установлен. Для четырёх чистых функций ИИ сравнение реальной сборки уже выполнено: различия ограничены явно перечисленными адресами компоновки, у сравнивателя их нет вовсе. Для остальных функций C-слоя такого совпадения машинных байтов не заявляется. Полная компоновка и весьEXE из восстановленногоC пока не получены; это остаётся отдельным объёмом работы даже при совпавших функциях и библиотечных модулях.

Компилятор, модель памяти и библиотека времени выполнения

Вывод, который действительно подтверждён

Исполняемый файл использует Borland-совместимую модель Large и стартовый модуль, побайтово совместимый с C0L.OBJ из исследованной поставки Borland C++ 3.1. Совместимость подтверждена на всём кодовом сегменте стартового модуля и на большой части CRT, а не только по строке copyright. Исследованный C0L.OBJ из Borland C++ 2.0 не совпал. Многие короткие библиотечные функции одинаковы в обеих поставках, поэтому их совпадение само по себе не определяет версию.

Единственную историческую версию компилятора установить этим сравнением нельзя. Не сравнивались все поставки Borland/Turbo C++ 3.x, а пользователь мог заменить библиотеку или стартовый модуль. Найденная BC3.1 — конкретная подтверждённая основа для повторной сборки, не доказательство идентичности исходной среды автора во всех деталях. Исходный текст C нельзя восстановить однозначно из совпадения машинного кода.

Метка __MMODEL из PUBDEF находится по image 0x0293 / file 0x1293. В оригинале там 04 C0, то есть 0xC004. В LIB/STARTUP/RULES.ASI исследованной поставки Large определён как 0x8000 + 0x4000 + 4: дальние указатели кода и данных. Соответствующий ключ BCC — -ml. Этот вывод проверяет значение маркера, а не предполагает модель по имени C0L.

Сохранённый лог сборки GPFTEST сообщает BCC 3.1 и Turbo Link 5.1. Прилагаемые здесь скрипты анализируют исходные .OBJ/.LIB; они не заменяют их скачанной таблицей сигнатур.

Адреса и метод сравнения

Все file-адреса — смещения внутри оригинального SNAKE.EXE; все image-адреса — смещения после загрузки MZ-образа без PSP и без добавления выбранного DOS сегмента. В этом файле MZ-заголовок имеет длину 0x1000, поэтому file = image + 0x1000 для байтов, действительно представленных в файле. Данные BSS за концом образа имеют file_offset: null в JSON.

tools/omf.py разбирает THEADR, LNAMES, SEGDEF, GRPDEF, PUBDEF/LPUBDEF, EXTDEF, COMDEF, LEDATA, LIDATA и FIXUPP. Учитываются переменные индексы OMF и frame/target threads. Неподдерживаемая релокация внутри развёрнутого LIDATA вызывает явную ошибку, а не молчаливое сопоставление неверной маски. Во всех исследованных CRT CODE-сегментах таких релокаций не встретилось. Неизвестные записи остаются в инвентаре записей.

Сопоставление выполняется следующим образом:

  1. Из LEDATA/LIDATA собирается сегмент с отдельной картой реально заданных байтов.
  2. Только поля, описанные FIXUPP, исключаются из прямого сравнения. Это необходимые изменения адресов при линковке, а не произвольная маска несовпавших байтов.
  3. Для CALL FAR с соответствующей pointer-релокацией дополнительно допускаются две конкретные пятибайтовые замены TLINK: 90 0E E8 xx xx и 0E E8 xx xx 90. Для JMP FAR с pointer-релокацией аналогично допускаются 90 90 E9 xx xx и E9 xx xx 90 90. Иные последовательности не принимаются.
  4. Ищется полное совпадение остальных байтов сегмента; фиксируется уникальность.
  5. Если адрес вызываемого символа независимо известен из другого совпавшего PUBDEF, проверяется фактическая цель вызова. Для оставшихся far-операндов проверяется соответствующая запись в таблице релокаций MZ.
  6. Совпавшие алиасы сохраняются как альтернативы. Короткая общая обёртка не получает безусловно имя исторического библиотечного модуля.

Подробные поля масок, смещения OMF-записей, все FIXUPP, цели вызовов и MZ-проверки находятся в analysis/crt_symbols.json. В analysis/crt_bc31_*.json и analysis/crt_bc2_*.json сохранены результаты только стабильного сопоставления; для итоговой атрибуции нужно использовать именно crt_symbols.json.

Повторение проверки

Из корня этого пакета. BC31_ROOT и BC20_ROOT — переменные окружения с путями к вашим установленным поставкам Borland C++ 3.1 и 2.0. python tools/crt_match.py \
  --exe original/SNAKE.EXE \
  --candidate Borland_Cpp_3.1 \
    "$BC31_ROOT/LIB/C0L.OBJ" \
    "$BC31_ROOT/LIB/CL.LIB" \
  --candidate Borland_Cpp_2.0 \
    "$BC20_ROOT/LIB/C0L.OBJ" \
    "$BC20_ROOT/LIB/CL.LIB" \
  -o build/crt-recheck.json

Для нового объектного файла, в том числе собранного восстановленного C:

python tools/omf.py dump module.obj -o module-omf.json
python tools/omf.py match module.obj --exe original/SNAKE.EXE -o module-matches.json

Вторая команда сопоставляет целый CODE-сегмент. Если в одном объекте несколько функций и требуется сравнить одну, Python API предоставляет Module.publics, Segment.data, Segment.initialized и Segment.fixups; границы можно взять по PUBDEF и следующему символу. Динамическая проверка и независимые реализации

Unicorn 2.1.4 исполнял исходные 16-битные инструкции выбранных процедур. Capstone 5.0.9 использован для листингов и анализа адресов. Основные дифференциальные проверки игровой логики привязаны к фиксированным смещениям и отклоняют неподходящий SHA-256 EXE.

Исходные ожидания для tests/LOGIC.VEC получены прямым исполнением четырёх процедур; восстановленный C не участвует в вычислении ожидаемого ответа. Его собранная Borland-версия читает эти векторы в DOS. Проверка движения отдельно сравнивает всё поле, все четыре состояния змей и счётчики с исходной процедурой; вызовы графики, звука и часов заменяются возвратами. Полное аппаратное поведение игры этим не проверяется.

Форматы реализованы независимо в Python и C89. Упаковщик GPF получает несжатые ресурсы и заново выбирает LZSS-совпадения. Исходные сжатые байты или сохранённый план токенов для сборки GPF не используются. SNK и REC собираются из типизированных полей и потока событий; неизвестные резервные байты и старые хвосты сохранены явно.

Дополнительные первичные источники

Сопоставление музыкальных форматов использует открытый код AdPlug mus.cpp и composer.cpp. Документация GPF отмечает, какие названия параметров заимствованы из этой реализации, а какие размеры и значения измерены непосредственно в файлах.

Для дополнительного сравнения также просмотрены опубликованные автором инструменты CTPAX-X для GPF и SNK. Они служили внешней сверкой уже полученных выводов. При расхождениях приоритет имеют исходные байты игры, её машинные процедуры и воспроизводимые проверки.

Как читать утверждения об идентичности

  1. Совпадение текста исходника: не установлено; по EXE оно в общем случае неоднозначно.
  2. Прямое совпадение функции: все байты выбранной законченной процедуры равны без изменений.
  3. Совпадение после адресной привязки: отличаются проверенные операнды линкера, остальные байты полностью равны. Каждая привязка перечислена в JSON; сам EXE не патчится.
  4. Совпадение поведения: проверенные входы дают те же результаты, но машинные байты могут отличаться.
  5. Совпадение пересозданного файла данных: исходный и новый файлы полностью равны, включая резервные области и хвосты.
  6. Совпадение всего EXE: не достигнуто этим пакетом.

Эти уровни не подменяют друг друга. Основная итоговая сборка, её контрольные суммы и результаты доступны в build/dos/verification.json, а машинное сравнение — в analysis/snk_rec_full_build_match.json и analysis/logic_full_build_match.json.
