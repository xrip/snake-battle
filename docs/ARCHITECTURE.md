# Внутренняя архитектура Snake Battle

## Границы восстановления и обозначение доказательств

Исследован поставленный `SNAKE.EXE`, размер **102326 байт**, SHA-256:

```
c4e064a1cf15e438017d4d6443817424f816ce4b749fcc279f2d97dc7bd86821
```

**Текущее состояние проекта:** полный EXE уже пересобран из C/ASM и оригинального CRT с совпадением всех 102326 байт. Полные игровые исходники находятся в `full/game/`, интерфейс — в `full/ui/`, остальные модули — в `full/`. Проверка всего файла — [comparison.json](../full/build/exact/comparison.json). Точный звуковой вклад пока собирается из символического ASM; его C-кандидаты не объявляются полностью совпавшими. Следующий абзац и часть таблиц ниже описывают дополнительные проверки отдельно выделенного переносимого ядра `src/logic.c`, а не текущий предел восстановления полной игры.

В `src/logic.c` и `src/logic.h` записан восстановленный читаемый **C89**: преобразования карт, сопоставление правил, выбор направления и изменение игрового состояния. Это самостоятельно названное представление машинных алгоритмов. Имена функций, комментарии, разбиение на файлы и исходное написание выражений из EXE восстановить однозначно невозможно. Для этого C-модуля не заявляется совпадение всего скомпилированного EXE по байтам. При этом четыре функции уже проверены реальной сборкой Borland C++3.1: сравниватель совпал86из86байт без изменений, два преобразования — по167из167байт после явного согласования адресов внешнихCRT-вызовов, полный сопоставитель —530из530байт после согласования адресовCRT и статических данных. Подробнее — `matching/README.md` и `analysis/logic_codegen_verification.json`. Карта идентифицированных функций и глобальных переменных находится в `analysis/semantic_symbols.json`.

Ниже «статически» означает вывод из инструкций и ссылок в конкретном EXE; «дифференциально» — сравнение восстановленного алгоритма с исполнением исходных 16-битных инструкций в Unicorn. Полный запуск DOS, всей графической подсистемы и всех экранов этим разделом не подтверждается. Это различие особенно существенно для функции выбора хода: её чистая логика выделена отдельно от записи повтора, рисунков, звука и обработки интерфейса.

В документе адрес `0729:1058` означает сегмент и смещение **относительно загрузочного образа MZ**, до прибавления DOS-сегмента загрузки. Для обычного кода:

```
image_offset = 16 * segment + offset
file_offset  = 0x1000 + image_offset
```

Размер заголовка EXE — `0x1000`. Для рабочих данных в BSS файлового смещения нет. Самоперемещающийся графический драйвер требует отдельного отображения адресов, описанного ниже.

## Компилятор и модель памяти

В файле по смещению `0x17794` находится строка `Borland C++ - Copyright 1991 Borland Intl.`. Код регулярно использует `CALL FAR`, `RETF`, четырёхбайтные указатели `segment:offset`, загрузки `LES`, 16-битные целочисленные операции и очистку аргументов вызывающей стороной. Вместе эти признаки соответствуют **16-битному Borland C/C++ с большой моделью памяти**, соглашением `cdecl` и дальними указателями. Строка с годом сама по себе не устанавливает точный выпуск компилятора. [Доказательство: EXE `0x17794`; функции `0729:000D`, `0729:1058`, вызов `0000:2B8E`.]

Практическая проверка выполнила сборку настоящим **Borland C++3.1 / TurboLink5.1**. Флаги `-ml -a- -k -O -r- -Z -G- -M` воспроизводят инструкции четырёх полностью разобранных функций ИИ, включая все530байт сопоставителя. `-r-` сохраняет переменные циклов в исходных позициях стека, `-Z` убирает повторные загрузки указателей, `-O` соответствует наблюдаемой обработке переходов. Более сильные `-O1`/`-O2` меняют циклы. Отдельное исследование библиотечных функций и признаков версии изложено в `docs/COMPILER_CRT.md`; с точки зрения этого раздела подтверждена конкретная совместимая инструментальная цепочка и воспроизводимая генерация кода, а не буквальный текст авторского проекта. [Доказательство: `matching/COMPILE.LOG`, `matching/AIMATCH.OBJ`, `matching/AIMATCH.MAP`, `analysis/logic_codegen_verification.json`.]

Игровые структуры имеют невыровненные 16-битные поля: якорь карты начинается с байтового смещения1, размер карты152, размер состояния змеи165. Поэтому в восстановленных заголовках явно задано байтовое выравнивание. Для Borland предусмотрены `far` и `#pragma option -a-`; для современной проверки — `#pragma pack(push,1)`. Присутствуют проверки размеров на этапе компиляции. [Доказательство: `0729:000D`, `0729:015B`, `0729:0BEC`.]

Главный DS в исследуемых функциях равен `1679` относительно образа. В частности, `DS:043C` содержит приращения X `{0,1,0,-1}`, а `DS:0444` — приращения Y `{-1,0,1,0}`. Направления имеют числовые значения0 вверх,1 вправо,2 вниз,3 влево. [Доказательство: данные EXE по файловым смещениям `0x17BCC`, `0x17BD4`; обращения в `0729:143C` и `0729:0BEC`.]

## Поле и рабочие записи

### Поле

Поле хранится в `DS:1B55` как `board[37][37]`. Индекс X внешний: адрес клетки равен `base + 148*x + 4*y`. Клетка занимает4байта: `owner` — 16-битный номер участника и `kind` — 16-битный тип. Всего массив занимает5476байт. Инициализатор `0729:081C` назначает тип0 внутри заданного прямоугольника и тип1 снаружи. Для основного поля используются координаты6…30 включительно: **25×25 клеток**, окружённых шестиклеточной защитной областью. [Доказательство: циклы `0729:081C`, адресация `0729:1493…1527`.]

Защитная область позволяет читать обзор13×13 вокруг любой игровой головы без отдельных проверок границ. При очистке клетки её `owner` сохраняется, а `kind` становится0; поэтому номер владельца пустой клетки не следует трактовать как действующего владельца. Восстановленный C сохраняет это поведение. [Доказательство: `0729:0B44`; дифференциальный отчёт `analysis/movement_c_verification.json`.]

### Состояние змеи

В `DS:3171` расположены четыре записи по165байт:

| Смещение | Размер | Поле |
|---:|---:|---|
| `+0x00` | 2 | Текущая длина |
| `+0x02` | 2 | Рабочий/накопленный счёт |
| `+0x04` | 2 | Поле, назначение которого в этом восстановлении не установлено |
| `+0x06` | 2 | Индекс головы в кольце |
| `+0x08` | 123 | 41тройка `{x:int8,y:int8,direction:int8}` |
| `+0x83` | 2 | Индекс цвета |
| `+0x85` | 32 | Рабочий графический дескриптор |

Тело хранится в кольцевом буфере из41элемента. Голова находится в `body[head_index]`; последующие части — по возрастающим индексам с остатком по41. Хвост имеет индекс `(head_index+length-1)%41`. При добавлении новой головы индекс уменьшается на1 по модулю41, что в EXE записано как `(head_index+40)%41`. [Доказательство: `0729:0A8B`, `0729:0B44`, `0729:0BEC`.]

Счёт не следует безусловно отождествлять с текущей длиной: код растит/уменьшает его вместе с длиной, а статистика боя использует накопленный результат нескольких раундов. Начальное выращивание прибавляет единицы к существующему счёту. [Доказательство: `0729:18EB`; обновление профиля в конце `0729:2327`.]

### Планировщик

Четыре флага `DS:1B4D` отмечают активных участников, четыре флага `DS:1B45` — ожидающих хода в текущем проходе. Счётчики находятся в `DS:1B41` и `DS:1B43`. Когда ожидающих не осталось, их набор копируется из активного. Случайное число задаёт начальный слот0…3; затем идёт круговой поиск первого ожидающего. Выбранный флаг сбрасывается. Это не равновероятный выбор из компактного массива активных слотов: вероятность зависит от промежутков между ними. [Доказательство: `0729:0F27`; логическое извлечение `sb_select_pending_slot`.]

`DS:340F` считает существующие змеи, включая неподвижный остаток длины1; `DS:3411` отмечает факт выполненного перемещения. Змея длины1 исключается из активного и ожидающего наборов, но окончательно исчезает только после поедания последнего сегмента. [Доказательство: `0729:0BEC`, подтверждено случаями длины2→1 и1→0.]

## Восприятие и правила ИИ

### Относительные типы клеток

На поле используются абсолютные типы:0пусто,1стена,4хвост,6тело,8голова. Перед сопоставлением правил строится обзор13×13. Если тип не меньше4 и владелец отличается от текущего участника, из типа вычитается1. Поэтому карты могут различать свои и чужие части. [Доказательство: `0729:1493…1527`.]

| Значение в карте/обзоре | Смысл | Особенность сопоставления |
|---:|---|---|
| 0 | Пустая клетка | Обычное сравнение |
| 1 | Стена | Обычное сравнение |
| 2 | Назначение редакторского символа не установлено | В сопоставителе обычное числовое значение; нельзя заменять пустотой |
| 3 | Чужой хвост | Обычное сравнение |
| 4 | Собственный хвост | Обычное сравнение |
| 5 | Чужое тело | Обычное сравнение |
| 6 | Собственное тело | Обычное сравнение |
| 7 | Чужая голова | Обычное сравнение |
| 8 | Собственная голова / обозначение якоря | Полностью пропускается сопоставителем |
| 9 | Не учитывать клетку | Полностью пропускается сопоставителем |

Значения8 и9 игнорируются независимо от группы и отрицания. Наличие8 в карте само по себе не создаёт проверку головы в этой позиции. Положение совмещения задаётся отдельными координатами якоря. [Доказательство: сравнения с8 и9 в `0729:1058`; 700дифференциальных случаев.]

### Карта7×7

Одна карта занимает152байта: общий режим группы1байт, координаты якоря X/Y по2байта, затем49троек `{group,negate,symbol}`. Порядок — X снаружи, Y внутри; клетка находится по `5+21*x+3*y`. Голова в обзоре находится в `[6][6]`, а клетка карты `[x][y]` сопоставляется с:

```
view[6 - anchor_x + x][6 - anchor_y + y]
```

Размер13 обеспечивает все положения якоря0…6 при размере карты7. [Доказательство: `0729:1058`; операции чтения SNK `0B33:0A4C`.]

Код использует пять логических групп. Массив семантики равен `{AND, OR, OR, AND, AND}` для индексов0…4. Та же таблица определяет общий режим карты. Для обычной клетки результат сравнения равен `(наблюдаемый_символ == символ_карты) XOR negate`. В корректных картах `negate` имеет значение0или1. [Доказательство: локальные массивы и ветвления `0729:1058`.]

В AND-группе любой провал обнуляет результат группы и оставляет его нулевым до конца проверки. Последующее совпадение не «восстанавливает» такую группу. В OR-группе считается число совпавших условий. Общий AND требует ненулевого результата каждой встреченной группы; общий OR суммирует успешные группы и требует хотя бы один успех. Карта без единой учитываемой клетки признаётся совпавшей со счётом0. [Доказательство: полный перевод `sb_match_card`; `analysis/game_logic_verification.json`.]

Результат имеет два16-битных поля `{matched,score}`. При неуспехе поле `score` иногда остаётся положительным: финальный цикл успевает прибавить счёт ранней группы, прежде чем встретить неуспешную AND-группу. Поэтому валидность обязательно проверяется отдельно. Сравниватель считает любые два неуспеха равными, успех всегда выше неуспеха, а два успеха сравнивает по счёту. Возвращаемые значения:0хуже,1равно,2лучше. [Доказательство: `0729:1002`, `0729:1058`; 64проверки сравнивателя.]

### Повороты и отражения

`0729:000D` отражает X: якорь становится `(6-x,y)`, клетка `[x][y]` берётся из `[6-x][y]`. `0729:00B4` поворачивает по часовой стрелке: якорь становится `(6-y,x)`, исходная клетка `[y][x]` записывается в `[6-x][y]`. Оба преобразования сохраняют все три байта клетки и общий режим. [Доказательство: по150дифференциальных примеров каждого преобразования.]

Перед боем `0729:015B` выделяет `0xAB00` =43776байт для кэша `4участника ×4поворота ×2отражения ×9карт ×152байта`. Шаг участника — `0x2AC0`, поворота — `0xAB0`, отражения — `0x558`. Сначала создаются обычный и отражённый варианты направления0, затем каждый из них последовательно поворачивается. В C-извлечении варианты вычисляются локально, без полного кэша. [Доказательство: множители и вызовы преобразований в `0729:015B`.]

### Выбор направления

Функция `0729:143C` исключает обратное направление `(previous+2)%4`, затем проверяет соседей. Типы1,5,6,7 запрещают ход; хвосты3и4 разрешены. После этого карты рассматриваются **в порядке их хранения**. Для каждого оставшегося направления сравниваются обычный и отражённый варианты; при равенстве выбирается обычный. Сохраняются направления с лучшим результатом. Как только очередная карта даёт хотя бы одно успешное сопоставление, следующие карты не рассматриваются. [Доказательство: `0729:1527…1800`.]

Если остаётся несколько направлений, случайное число0…3 задаёт начало кругового поиска первого разрешённого направления. Это тот же тип смещения вероятностей, что у планировщика участников. При отсутствии подходящих карт выбор производится среди законных направлений. При отсутствии законных направлений движение не выполняется. Поэтому в REC нельзя без состояния поля всегда чередовать «слот, направление»: запись направления зависит от возможности хода. [Доказательство: `0729:143C`, вызовы записи в `0729:18BC` и `0729:0FDE`.]

## Изменение состояния при ходе

Исходный `0729:0BEC` сначала устанавливает флаг движения, увеличивает длину и счёт ходящей змеи, превращает прежнюю голову в тело и создаёт новую голову в предыдущем элементе кольца. Затем анализируется целевая клетка. [Доказательство: прямой дифференциальный запуск180случаев.]

При попадании на хвост тип4 определяется его владелец. У владельца уменьшаются длина и счёт. Если длина стала1, единственный сегмент становится хвостом и участник перестаёт ходить. Если стала0, уменьшается количество существующих змей. Активный/ожидающий флаги и их счётчики корректируются независимо. Если хвост не съеден и параметр обычного хода установлен, убирается собственный старый хвост. В конце новая клетка получает владельца ходящей змеи и тип8. Поедание собственного хвоста следует из той же последовательности операций и не требует отдельной ветки. [Доказательство: `0729:0BEC…0F26`; `sb_apply_move`.]

Начальное выращивание `0729:18EB` создаёт первую часть в элементе40, затем вызывает ход без обрезания собственного хвоста, пока длина не достигнет10. Такая последовательность используется в анимации входа `0729:1BB0`. Восстановленная `sb_seed_snake_step` включает изменение состояния, но не рисунки ворот и задержки. [Доказательство: исходные вызовы и сравнение длины с10.]

## Профили, счёт и повтор

Рабочие указатели четырёх профилей находятся в `DS:34D7`. В профиле карты начинаются со смещения `0x69` =105, количество карт хранится в16-битном поле `+4`. Поле `+6` накапливает завершённые раунды. Поле `+8` обновляется после боя: учитывается отклонение накопленного счёта от `10 × завершённые_раунды`, делённое на обновлённое суммарное количество раундов. Ненулевое отклонение с нулевым целочисленным частным даёт изменение+1или−1. [Доказательство: загрузчик/сохранительSNK; обновления образа `0x9EA3`, `0x9EA6`, `0x9EF2`.]

Модуль REC `0E92` сначала обрабатывает кодированный заголовок с профилями, затем переключается на поток сырых полубайтов. ТокенE сопровождается счётом присутствующих участников; D завершает текущий повтор. В исходной функции открытия записи отсутствует `O_TRUNC`, поэтому после текущего логического конца могут оставаться байты более старой длинной записи. Их нельзя считать дополнительными раундами текущего повтора. Полные схемы, поля и правила сохранения хвоста изложены в отдельном описании SNK/REC. [Доказательство: `0E92:0067`, флаги открытия `0x8104`; разбор модулем форматов.]

## Кодированный графический драйвер

В EXE присутствует небольшой самостоятельно декодируемый блок драйвера. Его исходный заголовок расположен по файлу `0xFD66`. Шесть байтов перед ним принадлежат выравниванию/предыдущей области; начало сегмента `0ED6` в `0xFD60` не совпадает с началом заголовка. В заголовке находятся CALL на обёртку, маркер `0x1234`, смещение полезного кода `0x00B0`, контрольное значение и длина. [Доказательство: байты заголовка и обёртка файла `0x12D36…0x12DB4`.]

Кодированные данные занимают `[0xFE16,0x12D36)`, **12064байта**. Декодирование использует8-битное состояние:

```
state = 0
для каждого cipher:
    state = ROL8(state, 1)
    plain = cipher XOR state
    state = (state + plain) mod 256
```

Обратное преобразование даёт исходные байты точно. SHA-256 декодированного блока:

```
329e58a15e80df4c559db734a719a2837346ad3e82a73ca29c8ddeda1d063c90
```

Обёртка также считает контрольную сумму, но в исследуемом EXE инструкция по файлу `0x12D80` является безусловным переходом, обходящим ветвь отказа. Это наблюдаемое свойство входного файла; восстановительные инструменты не меняли эту инструкцию. [Доказательство: оригинальные байты; `analysis/sprite_driver_verification.json`.]

После декодирования исходный инициализатор копирует первые `0x2EC0` =11968байт блока вниз на `0x16` =22байта: из адреса образа `0xEE16` в `0xEE00`. Последние96байт — сам инициализатор — не копируются. Исходный CALL в заголовке по адресу образа `0xED66` заменяется последовательностью `EA B0 00 D5 0E`, то есть дальним переходом `0ED5:00B0`. [Доказательство: полный запуск обёртки и инициализатора в `tools/verify_driver_init.py`; `analysis/sprite_driver_init_verification.json`.]

Для декодированных инструкций справедливо:

```
условное исходное файловое смещение = 0xFD66 + offset_драйвера
адрес в образе после инициализации = 0xED50 + offset_драйвера
```

Например, таблица диспетчера `CS:0102` происходит из декодированных байтов, соответствующих файловому смещению `0xFE68`. Линейный листинг `analysis/sprite_driver_linear_listing.txt` использует условные файловые смещения; он содержит также области данных, которые дизассемблер может представить как инструкции. Такой листинг не является доказанной картой всех функций драйвера. Файлы `sprite_driver_plain.bin` и декодирующий скрипт служат материалом анализа; C-модуль игровой логики не встраивает этот машинный код.

## Оставшиеся ограничения

Авторские имена и точный текст C не могут быть однозначно извлечены из бинарника. В текущем `full/` восстановлены оболочка, редактор, все прикладные модули и точные символические представления драйверов. Полная смешанная сборка и весь EXE совпали байт-в-байт. Отдельной открытой задачей остаётся точная компиляция обычных звуковых процедур непосредственно из C; текущий ASM этого блока не выдаётся за доказанный исторический исходный язык. См. [SOUND_REBUILD_STATUS.md](SOUND_REBUILD_STATUS.md).

У дополнительных переносимых моделей остаются собственные границы проверки. `sb_choose_direction` из `src/logic.c` проверен через Python-модель, но эта проверка не заявляется как исполнение исходного `0729:143C` со всеми побочными эффектами. Это не отменяет отдельного полного байтового совпадения `full/game/GAME.C` в итоговом EXE. В таблице состояния змеи остаётся неименованное поле `+4`; смысл редакторского символа 2 не установлен. Совпадение исполняемых байтов не подменяет установленную семантику каждого имени и каждого резервного поля.
