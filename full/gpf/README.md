# Полный модуль GPF и исходный декодер LZSS

`GPF.C` восстанавливает все девять функций исходного модуля, включая его
первоначальные ошибки обработки ресурсов. Настоящий Borland C++ 2.0 компилирует
этот файл в **1495 байт кода, совпадающих с исходным EXE целиком** после обычного
разрешения OMF-ссылок и исходных преобразований дальних вызовов TLINK.
Проверены также порядок функций, все публичные адреса, позиции, порядок и
сегментное представление MZ-релокаций. Исходные названия функций неизвестны;
использованы описательные восстановленные имена.

Borland C++ 3.1 на том же C-тексте даёт другой машинный код. Для этого модуля
выбран реально проверенный профиль Borland C++ 2.0; готовый OBJ совместим с
Borland TLINK 5.1 и стандартной библиотекой 3.1, используемыми остальной игрой.
Совпадение доказывает воспроизводимость данным инструментарием, а не
единственность исторического номера версии компилятора.

| Вклад | Адрес образа | Длина | Доказательство |
|---|---:|---:|---|
| GPF C CODE | `11DB:0006`, линейный `0x11DB6` | 1495 | `module_code.json` |
| GPF DATA, handle = −1 | `1679:0F06` | 2 | `module_data.json` |
| GPF BSS | `1679:4104` | 56 | `module_bss.json`, проверка распределения |
| LZSS CODE со словарём | `1238:000D`, линейный `0x1238D` | 4238 | `module_lzss.json` |

Смещения в файле EXE больше линейных адресов образа на `0x1000`.
Область LZSS содержит 4096 нулевых байт изменяемого словаря и 142 байта
настоящих 8086-инструкций. Вход декодера — `1238:100D`. Нулевые байты словаря
являются исходными данными, а не машинным кодом, скрытым в массиве.
Один нулевой байт между концом LZSS (`image 0x1341B`) и следующим модулем
создаётся выравниванием следующего сегмента по границе слова.

## Сборка

Из корня проекта, с установленными оригинальными компиляторами и DOSBox:

```sh
python full/compile.py full/gpf full/gpf/build GPF.C \
  --compiler "$BC20_ROOT" \
  --flags '-ml -a- -k- -O- -r- -Z- -G- -K'
python full/gpf/assemble.py --compiler "$BC31_ROOT"
python full/gpf/check.py
```

Для диагностического перебазирования внутренних вызовов `check.py` использует
Capstone. В итоговой проверке целого модуля это преобразование не применяется.
Код проверяется без произвольного маскирования байтов и без чтения эталонных
инструкций как входа сборки. Эталонный EXE нужен только для сравнения.

`GPF.H` задаёт 33-байтовый заголовок и 22-байтовую запись каталога.
В BSS компилятор размещает запись после 33-байтового заголовка и одного байта
выравнивания: `gpf_header` находится по `DS:4104`, `gpf_entry` — по `DS:4126`.
Незаполненная BSS не имеет хранимых байтов в EXE, поэтому её отчёт честно
проверяет размер и расположение символов, а не «равенство файловых байтов».

## Сохранённое поведение оригинала

`gpf_close` не сбрасывает дескриптор в −1. `gpf_alloc` не освобождает первый
буфер при ошибке выделения распакованного буфера. Загрузчик четырёх плоскостей
не освобождает входной сжатый буфер. Четыре его внешних far-pointer lvalue
находятся по адресам `DS:40A6`, `40A8`, `40AA`, `40AC`: пары слов действительно
перекрываются. Это подтверждено исходными инструкциями, а не предположено по
декомпиляции. Отдельные символы и их исходные адреса сохранены в
`bindings.json`; заменять их обычным массивом указателей нельзя.

Функция показа на экране сохраняет две короткие исходные последовательности
inline ASM, управляющие регистрами VGA Sequencer. Всё остальное в `GPF.C`
является настоящим C. Самостоятельный исходный ASM-декодер находится в
`LZSS.ASM`, с метками и командами, без вставки массива опкодов.

Подробная спецификация архива и ресурсов: `../../docs/GPF_RESOURCES.md`.
