# Общая сборка восстановленных модулей

`build.py` собирает настоящие C-файлы оригинальными DOS-компиляторами и вызывает
оригинальный TLINK. Эталонный `SNAKE.EXE` не является входом сборки. Он нужен
только отдельному `verify.py`, который сравнивает результат компиляции и
релокации с оригиналом.

Статус основного C-пути определяется текущими `build.json`, `verification.json`
и `native/LINK.LOG`. В `modules.json` SOUND остается `pending`: машинный код
его обычных C-функций пока не совпал с результатом исторического компилятора.
Отдельный `exact_sound.py` уже воспроизводит весь исходный EXE побайтно,
используя для этого участка символическую ассемблерную спецификацию. Это не
доказательство исторического ASM-источника или завершения C-matching;
граница результата и команда сборки описаны в `EXACT_BASELINE.md`.
Неопределенные ссылки не заменяются заглушками.
TLINK способен записать EXE и при ошибках; такой результат сборочный скрипт
удаляет, оставляя диагностический MAP и журнал.

## Что поступает на вход

`modules.json` задает порядок объектов, компилятор, флаги, исходные начала
CODE/DATA/BSS и проверяемые размеры contributions. Основной прикладной код
компилируется Borland C++ 3.1 в large memory model. Главная функция требует
`-k`, остальные восстановленные модули — `-k-`. Для аппаратного ввода нужен
`-B`: компилятор передает свой ASM оригинальному TASM, как в исходной сборке.
GPF требует Borland C++ 2.0 и своих флагов. LZSS записан нормальными командами
ассемблера и метками; его инициализированный 4096-байтный словарь является
данными алгоритма.

`prepare.py` копирует исходники и заголовки из соседних каталогов в `src/`.
Файлы авторов модулей при этом не изменяются. В копии добавляются определения
общих данных из `globals/*.inc`:

- таблицы координат, прямоугольников, направлений и цветов;
- заголовки, правила и состояние змей;
- строки интерфейса и имена ресурсов;
- указатели изображений, шрифтов и файлов;
- состояние игрового поля, редактора, записи и аппаратного ввода.

Это C-структуры, массивы типизированных записей, числовые и строковые
инициализаторы. Порядок полей и `sizeof` проверяются самим 16-битным
компилятором. `globals/manifest.json` документирует поля, размеры и адреса.
Неиспользуемые или пока не названные поля явно сохраняют нейтральные имена;
им не приписывается недоказанная семантика.

## Общие символы и перекрывающиеся поля

Разные восстановленные модули используют разные имена одного исходного
объекта. Кроме того, оригинал адресует внутренние поля структур и середину
строк как самостоятельные символы. `aliases.py` добавляет к OMF обычные
записи PUBLIC, указывающие на существующие функции или поля настоящих
C-объектов. После этого ссылки разрешает TLINK.

Скрипт не меняет SEGDEF, LEDATA, LIDATA или FIXUPP. Он проверяет, что все эти
записи побайтно прежние. Адрес алиаса функции вычисляется по реальному
PUBLIC, выданному компилятором; поэтому неправильную длину предыдущей
функции таким способом скрыть нельзя. Алиас поля вычисляется от начала
реальной C-структуры. Машинные инструкции, дополнительные переходы и
подставные участки кода для совместимости имен не создаются.

Сохранен и неудобный ABI оригинала: GPF обращается к экранным плоскостям как
к перекрывающимся четырехбайтным указателям с шагом два байта. В модуле
рендеринга это исходный массив двухбайтных значений. Объявления в вызывающих
модулях оставлены прежними, а PUBLIC указывают на подтвержденные смещения.
Изменение типов на более привычный массив far-указателей нарушило бы код и
раскладку оригинальной игры.

## Запуск

Из каталога пакета:

```sh
python full/build/build.py \
  --bc31 /path/to/BORLANDC \
  --bc2 /path/to/BC2 \
  --dosbox /path/to/dosbox
python full/build/verify.py --reference original/SNAKE.EXE
```

В каталогах компиляторов должны находиться оригинальные `BIN` и `INCLUDE`.
Компиляторы и их runtime не заменяются современным компилятором. В рабочей
среде анализа пути по умолчанию ведут к уже проверенным дистрибутивам.

Для повторной диагностики линковки существующих OBJ есть `--skip-compile`.
`--stage-only` создает `native/LINK.RSP` и `LINK.BAT` для ручного запуска DOS.
Обычная сборка заново компилирует все готовые исходники, включая GPF и LZSS.

`full/link/runtime/layout.json` задает порядок оригинального startup и
извлеченных из оригинальной библиотеки runtime-объектов. Они передаются
TLINK вместе с восстановленными объектами; код runtime не копируется из
эталонного EXE. В отдельном `native_verification.json` доказана идентичность
выбранных библиотечных contributions.

## Проверка результата

`verify.py` проверяет каждую полную CODE/DATA contribution: все ее байты,
адреса PUBLIC, действительные OMF fixups и представление релокаций MZ,
включая порядок. BSS не содержит байтов в файле, поэтому для него проверяются
размер выделения, отсутствие инициализированных данных и адреса полей.
Подробные результаты записываются в `proof/`, сводка — в `verification.json`.

Проверка contribution использует подтвержденные адреса внешних модулей и
допустима до их готовности. Она не означает, что вся программа уже связана.
Успешная нативная линковка и полное побайтовое сравнение EXE — отдельные
условия. Они включают общий порядок объектов, выравнивание, заголовок MZ и
таблицу релокаций, а не только совпадение инструкций отдельных функций.
