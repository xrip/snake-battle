# Исходная линковочная компоновка и проверка OMF

Инструменты этой папки разрешают реальные OMF-fixup записи и проверяют
полученный код по исходным адресам. Они не берут инструкции из исходного EXE
в качестве строительного материала. Неподдерживаемая или неизвестная ссылка
приводит к явному отказу проверки, а не к маскированию отличий.

## Стандартная библиотека

`runtime_layout.py` извлекает оригинальные объектные модули из Borland C++ 3.1
`C0L.OBJ` и `CL.LIB`, восстанавливает их порядок, CODE, DATA и BSS-вклады и
генерирует `runtime/layout.json` и `runtime/bindings.json`.
Выбраны 91 библиотечный модуль и отдельный стартовый C0L. Все 87 непустых
CODE-вкладов покрывают **16115 байт** от `image 0` до `0x3EF3` без пробелов.

Отдельная настоящая сборка `runtime/PROBE.C` через оригинальный BCC/TLINK
подтверждает выбранный порядок независимо от программного OMF-резолвера.
Этот короткий файл служит только проверке компоновки и не является игрой.
Его массивы резервируют нужные объёмы DATA/BSS; они не содержат скопированного
игрового кода. `check_native_runtime.py` явно переносит только настоящие
MZ-релокации DGROUP из адреса короткого примера в исходный адрес игры и
проверяет **16115 байт CRT-кода и 1382 байта CRT-данных**. Проверяются также
порядок и точное SEG:OFF-представление всех 13 релокаций CRT.
Результат: `runtime/native_verification.json`.

| Область DGROUP | Диапазон смещений |
|---|---|
| C0 DATA и выравнивание | `0000..0094` |
| DATA игры | `0094..134C` |
| DATA CRT и выравнивание | `134C..1800` |
| Векторы вещественных преобразований | `1800..1808` |
| INIT records | `1808..1826` |
| BSS игры | `1826..61F6` |
| BSS CRT и выравнивание | `61F6..6290` |
| STACK | `6290..6310` |

В исходном EXE `DGROUP=1679`, `SS=1CA2`, `SP=0080`.
Инициализированная часть заканчивается по `image 0x17FB6`, а расчёт
минимального размещения неинициализированной части даёт исходное
`e_minalloc=0x4AF`.

TLINK резервирует размер заголовка по исходному числу потенциальных
сегментных fixup, до оптимизации дальних вызовов и переходов. Для контрольной
сборки 113 таких ссылок дают 1024-байтовый заголовок, хотя после оптимизации
остаются лишь 13 MZ-релокаций. Поэтому размер заголовка полного EXE нельзя
вычислять только по оставшимся 879 релокациям и затем исправлять вручную.

## Проверка восстановленных модулей

`verify_object.py` проверяет отдельную функцию, разрешая её внешние символы
по `bindings.json` и проверенной карте CRT. Каждая функция может временно
иметь собственную заявленную позицию, поэтому такой результат сам по себе
не доказывает правильное расположение всего модуля.

`verify_module.py` проверяет весь вклад сегмента по одному начальному адресу,
все известные PUBLIC offsets, все байты и точную последовательность
MZ-релокаций. Только этот отчёт выставляет
`complete_segment_contribution_proven=true`.

```sh
python full/link/verify_module.py full/gpf/build/GPF.OBJ \
  --segment 1 --address 11DB:0006 --length 1495 \
  --bindings full/gpf/bindings.json -o full/gpf/module_code.json
```

Необязательная диагностика `--structural-internal-calls` в проверке отдельных
функций учитывает сдвиги известных внутренних `E8`-вызовов, когда предыдущие
функции ещё не восстановлены точно. Это отдельный вспомогательный отчёт.
Он не изменяет raw-проверку, статус PASS, исходный OBJ или доказательство
полного модуля.

## Финальная линковка

`stage_link.py` получает упорядоченный список восстановленных игровых OBJ и
создаёт `LINK.RSP`: C0L, игровые объекты в исходном порядке, затем 91 исходный
CRT-объект. Сборка выполняется обычным оригинальным TLINK. Этот инструмент
не читает исходный EXE, не добавляет подложку и не создаёт фиктивный код для
заполнения неизвестных промежутков.

```sh
python full/link/stage_link.py --runtime full/link/runtime \
  --game START.OBJ INPUT.OBJ MUSIC.OBJ OTHER_GAME_OBJECTS.OBJ \
  --output build/full --name SNAKE
```

Это пример формы команды; список игровых модулей должен быть полным.
Публичные имена, восстановленные нами, могут отличаться между C-файлами.
При интеграции допустимы OMF PUBLIC aliases с тем же адресом; trampoline-код
для таких алиасов не нужен и нарушил бы исходную компоновку.
